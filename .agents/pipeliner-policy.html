Project-agnostic delivery governance

Pipeliner

One evidence-first path from a coherent GitHub Issue to an exact, verified release and clear PM Testing. The repository profile supplies project-specific details; the lifecycle supplies the safety contract.

Lifecycle

1 · Backlog

Research, clarify, approve, create, classify, and read back one implementation-ready Issue.

2 · In Progress

Reserve the single active slot, specify, implement test-first, validate, and publish a linked pull request.

3 · In Review

Complete agent QA, remediate every finding, identify the exact candidate, and prepare PM Testing.

4 · Done

Release through the configured strategy, verify, receive candidate-specific PM acceptance, then close and read back.

Agent-owned Project movement

The agent performs routine GitHub Project transitions and immediately verifies the resulting Status, metadata, assignment, Issue state, linkage, and active count. The PM never has to drag a card to keep the pipeline coherent.

Exactly one Issue may be active. Merge, green CI, deployment health, and silence are evidence—not completion or approval.

Release strategies

Immutable promotion

Build once, verify the review candidate, obtain exact approval, and promote the same artifact without rebuilding.

Direct Production

Deploy the reviewed default-branch revision, verify Production, then keep the Issue open for PM Testing and exact completion approval.

Multi-environment

Validate the same code candidate independently on every required native host or environment. One approval cannot substitute for another.

Project Manager QA

Every review or release handoff gives the PM the exact target, prerequisites, numbered actions, expected results, regression checks, candidate identity, limitations, and the precise approval phrase when approval is the next gate.

When repository evidence cannot resolve a material behavior, topology, or recovery decision, the agent pauses and asks the PM focused clarifying questions.

Repository discovery

Branch protection and rulesets are optional and never enabled by default. The agent asks the PM whether protection is wanted and, if so, which branches and rules to enforce. Existing controls remain unchanged until an explicit decision. Agent quality gates and PM approval still apply without branch protection.

Begin with an explicit target or intent to create a repository. The agent resolves missing name, purpose, owner, visibility and destination, then verifies access and identity. Failed access is not proof of absence. Existing customized policies and unrelated work remain protected.

The interview establishes runtime systems, developer availability, required local QA turns, PM ownership, setup, cleanup and release destinations. Material unanswered choices pause dependent work. Bootstrap does not deploy the application.

Local QA and ownership

QA turns are independent of release destinations. One developer may test Windows and macOS; two developers may both test Windows. Each required turn runs the full suite locally and records the exact candidate, owner, environment, session, results, PM Testing and cleanup.

One developer on one environment needs no baton. Otherwise, the outgoing owner verifies every gate and confirms the exact candidate is available to the next environment. The incoming owner verifies identity and acknowledges pickup. Waiting remains In Progress on the same Issue; missing hosts never count as a pass.

Application, native-package and container-image builds stay on compatible local systems. GitHub Actions retains reviewed lightweight checks, including inspection of every indirect command chain. Local evidence never fabricates a GitHub check result.

Track test-owned processes, containers, images, volumes, artifacts and workspaces by exact identity. Clean up after successful and failed runs, preserve unrelated resources, and verify removal. Resources retained for PM Testing need an owner and cleanup trigger; final removal remains a required gate.

Candidate integrity

An approval belongs only to the configured source commit, Git tree, artifact digest, rendered configuration, deployment revision, native host, or validation session that defines that candidate. A material identity change invalidates approval and returns the work to verification.
