Research and existing flow

Current Mac: macOS 27.0.1 (26A434), arm64; Xcode 27.0, first-launch check exit 0. A valid Apple Development identity exists; distribution identity/notarization is not established. The installed ServiceManagement SDK requires signed bundled user agents, reports enabled/requires-approval/not-registered/not-found, supports relocation through BundleProgram and warns that unregister kills a registered service. Apple background-task guidance describes visible OS controls and macOS 26+ consent prompts. Never override these controls or install an MDM profile. Pinned Electron 44.4.5 exposes native SMAppService registration/status; actual local signing and service behavior must be measured.

The current main process is already the sole broker/scheduler owner, with both Electron single-instance protection and an exclusive SQLite execution owner. PM IPC authenticates the exact restricted main frame. Development close verifies worker stop/pause and preserves captured policy and claims. Protected host policy already contains both background settings. The new work reuses these modules; it does not introduce a second executor, scheduler, socket server or agent-facing service endpoint.

Smallest correct architecture

A signed bundled per-user bootstrap helper opens only its own verified containing Pipeliner application through LaunchServices with a fixed background argument. This keeps the executor outside the registered bootstrap job, so unregister cannot kill a live executor before safe pause completes. The application hosts the same broker modules in foreground or background mode, with one ownership lock. Reopening creates a restricted UI attached to that same owner. The helper cannot launch arbitrary paths or accept commands, settings, secrets or repository content.

Service registration is explicit PM intent. The native bootstrap may be invoked at a subsequent login because that is SMAppService behavior; the host checks protected background/start-at-login policy and actual OS authorization before any connection, worker or scheduling effect. When login start is off it exits without opening the UI or doing work. Explain this distinction honestly. There is no KeepAlive loop that defeats explicit quit. A normal quit pauses and exits; login execution is permitted only by the separate PM setting. No root daemon, manual LaunchAgents file, privileged operation or OS wake is added.

Background capability remains unavailable in the unbundled development launcher. A verified signed containing bundle and reviewed fixed helper/plist establish capability; actual native authorization establishes effective background execution. Requires-approval/denied remains blocked with an explicit System Settings action. Startup never auto-registers or re-registers an OS-disabled service.

Acceptance cases and risks

  • Fresh/off state performs no registration, provider request or background work. Scheduling cannot enable host background. An unpackaged host cannot claim background qualification.
  • PM previews preserve saved state until apply; login remains off when background is enabled. Repeated apply has one policy version and one registration attempt. Capability/scope/version changes invalidate previews.
  • OS requires-approval or revocation prevents effective background work. Never auto-click or re-register to overcome it. Opening Settings requires a current direct PM action.
  • Authorized UI closure leaves the same host owner and scheduler alive; reopen returns current repository/Issue/policy state and exact restricted IPC. Unauthorized closure pauses and exits.
  • Disable first fences checks/effects, verifies worker pause and persists the disabled intent; then removes service registration. Failed pause/removal remains visible and recoverable, never a false disabled result.
  • Explicit quit and signal safely pause and close stores. Abrupt death keeps reservation/journal uncertainty for existing reconciliation; no blind provider/GitHub write replay. Repeated close/quit cannot run teardown twice.
  • Sleep pauses effects; wake does one check. Actual session logout/reboot cannot be inferred from an emitted test event. Record those cases pending if they cannot be exercised without interrupting unrelated user applications.
  • Native helper and package verification rejects tamper, unsigned/unqualified bundle, arbitrary target/argument, foreign service and inaccessible private storage. Only exact owned test registration/PIDs/files can be removed.

Native registration may need Human OS consent or a signing-key access prompt. Finish code and all independent safe evidence first; stop only at the actual external control. A development signature cannot establish Gatekeeper distribution trust. The final installer, trust/notarization, full sleep/reboot/logout and 24-hour workload matrix remain later qualification work. Do not weaken controls to turn those limits into passes.
