Issue #48 — budgets and qualified Dev takeover

Final Draft 1.0 D-17. Base: 6704946e988757f9c866a42bf2a1bdbb5b325b6a; tree 9f09624bcc27607b45b96d9528bd1e9fc09d8ee4. Depends on completed D-16 / Issue #46. Mappings: R-18–R-20, R-23, R-31, R-42; NFR-11, NFR-16, NFR-19; T-06, T-07, T-09, T-15; S-02, S-08.

Evidence and decisions

Settings already contain turn, transient-attempt, remediation and timeout limits, with automatic takeover off and no fallback. The Development ledger resets step turns on a visit, while the engine and supervisor measure a whole run from creation. The connections manager fences even transient failures, preventing a bounded retry. Runtime Dev binding is immutable and currently has no takeover journal. Fix these existing boundaries; use the standard library and installed SQLite without new dependencies.

Official Ollama Chat API and usage documentation expose provider-reported token receipts. Receipts do not establish a pre-dispatch monetary or token hard bound. Current adapters therefore keep metric-capability lists empty; optional hard caps stay unavailable and are rejected before execution. Report known counts separately from unavailable usage and USD. GitHub guidance requires respecting retry guidance and reconciling effects; existing write journals remain authoritative.

Focused design

  1. Extend hash-protected Development state with per-step turn counts, accumulated active execution time, durable provider-operation attempt/backoff state, remediation count, current captured Dev and takeover history. Account before dispatch. Revisits, epoch changes and fallback never reset these values. Legacy records remain readable; missing durable timing evidence blocks dispatch for verified recovery rather than creating empty counters.
  2. Use per-step active deadlines. Checks use the build/test limit; agent steps use the agent limit; integration uses the control limit. Pause seals elapsed time after verified worker termination; a future resume continues the remaining budget. Crashed active time is charged conservatively until recovery. Add optional validated step timeout through existing graph chat/editor, preserving unchanged graphs.
  3. Classify only explicit temporary transport/timeout, HTTP 408/429/5xx responses as transient. Keep three total attempts by default, approximately 2/8 seconds plus bounded jitter, and honor sanitized Retry-After guidance within the remaining deadline. Every provider attempt consumes a model turn; absent/failed response usage becomes unavailable. Authentication, revocation, malformed output, policy denial and uncertain mutations do not retry. Read-only retry is bounded; writes retain existing intent/readback-before-replay rules.
  4. Capture the explicitly configured qualified fallback order with the initial run. No dynamic model/provider discovery or implicit destination. A host-only runtime assignment journal advances the worker epoch while retaining immutable original run/policy/graph/limits and reservation. Before each takeover, verify the former worker stopped, sole live active Issue/readiness/dependencies, unchanged source and current worker candidate, and any published branch/PR. Require fresh typed continuity evidence. Select only the next still-authorized captured qualified fallback.
  5. Automatic takeover is eligible only for a classified provider transient failure with remaining turns, attempts and deadline. Stop the former worker and close its provider lease before changing assignment. Runtime and ledger recovery reconcile the durable assignment if interrupted; uncertainty blocks. Same policy, graph, candidate, checked evidence and QA state remain bound. Removing fallback permission, disconnecting a connection or disabling takeover revokes the next action immediately.
  6. Expose actual current Dev, captured turn limits, retry/remediation count, takeover history and reported-versus-unavailable usage through existing local status. Keep controls available without a model. Existing Settings and chat remain the PM authority; the execution agent cannot clear counters or configure fallback. Settings edits retain their established future-run effect; this Issue does not add active-run budget escalation.

Ordered implementation plan

  2. Implement shared durable budget and failure-classification primitives, then connect engine/provider retry and safe connection health.
  3. Add backed-up runtime assignment migration and stopped/continuity checks; wire the manager, supervisor and captured fallback pool.
  4. Update graph timeout controls and readable status; inspect keyboard/narrow/zoom behavior through the native qualification harness.
  5. Run focused faults and the complete configured suite; review the complete diff and security/recovery paths. Record actual native evidence and cleanup. Publish supporting PR with complete Showcase and accurate unproven boundaries.
  6. Under standing intermediate-goal authority, integrate the exact reviewed tree using allowed repository method, verify readback and close this Issue. Final complete-app Human PM Testing remains deferred; do not fabricate Human approval.

Acceptance criteria

  • 20 default turns per step and 100 per Issue include every attempted provider call and persist across visits, retry, recovery and takeover. Three transient attempts and three remediation cycles remain finite and durable. Limits cannot increase through agent text or epoch change.
  • Active time consumes the appropriate captured deadline; verified waiting does not consume execution time. Resume cannot reset spent time. Backwards time, missing continuity and pending effects block.
  • Only classified transient operations retry; safe guidance is bounded by remaining deadline. Failed or missing usage is unavailable, never a successful zero-dollar claim. Unsupported hard metrics remain unavailable.
  • Fallback off/empty remains the default. Enabled fallback must be explicitly captured, qualified and ordered. Prior worker stop and exact current work continuity precede a new Dev and epoch. One active Issue/reservation persists; QA and budget blockers cannot be bypassed.
  • Legacy framework adoption behavior and unrelated primary files remain preserved. Configured suite passes; native evidence and cleanup are accurately reported. No unresolved high/critical scoped finding remains.

Non-goals

Scheduler, background service, additional provider execution adapters, secret transfer, implicit connection selection, cross-platform support, installers, final Human acceptance, and monetary estimates as hard limits. This work qualifies existing restricted Node/Git execution; it does not prove arbitrary toolchains or native installation.

Risks and recovery

  • Takeover crosses runtime/ledger/worker stores. Persist assignment first, then reconcile the ledger by the same candidate and higher epoch; interrupted or uncertain writes block rather than restart from source.
  • New runtime schema must back up the previous readable SQLite version before transactional migration. Original run binding remains immutable. Corruption or migration failure preserves the readable prior store and stops dispatch.
  • Retry may incur charged requests with no receipt. Mark unavailable, preserve counts and never use unknown consumption to enable a hard cap.
  • Current qualified Dev catalog may contain only one executable model. An empty/unqualified fallback pool remains blocked; synthetic takeover tests must not be presented as live parity between providers.
  • Command execution retains its existing five-minute per-command boundary while the check step receives the configured total build/test budget. Longer native build paths remain separately qualified work.
