Evidence and affected flow

On source ada2f4d214ea3b2ecf4dc4aad4d06d8eb15a4816, desktop/connections/github.mjs checks the registered App's exact id, public client id, owner and permission map in inspectGitHub, after the device grant completes. githubAdapter.connect starts the device request and native prompt first. Thus a changed registration is detected only after authorization. The actual reviewed registration matched before the native trial; this finding does not assert a live permission change.

The actual packaged native trial on that source returned to Chat with checked access to one repository and seven Projects; a deliberate access refresh also returned checked. This connection evidence covers neither the full operation map nor Human acceptance. GitHub documents that App user access comes from the intersection of user and registered App permissions/resources, and supports the device flow without a packaged client secret. Official GitHub authorization contract (reviewed 14 October 2026).

Specification and ordered plan

  2. Extract the existing exact registration comparison into one private helper. Invoke it before starting scoped App authorization. Retain the existing post-authorization and access-refresh check through inspectGitHub, including detection of a registration change during the grant.
  3. Keep the separate PM-directed setup OAuth path unchanged. Exercise its existing flow without a scoped-App preflight; test a valid scoped flow's preflight, device grant, effective-access readback and prompt cleanup.
  4. Run focused regressions, the complete configured quality suite, review the exact diff, and build a new source-bound Mac candidate. Operate the actual app as the Agent, verify preserved connections/access and normal quit, then update the candidate and Showcase evidence.

Acceptance criteria

  • Only the exact approved registration can begin the scoped device authorization. A failed or cancelled preflight produces no device request or native authorization surface.
  • Valid scoped authorization still returns verified effective access; a later registration change still fails closed. The owned prompt closes on grant success or failure.
  • The separate setup OAuth connection retains its deliberate broader setup semantics; existing connections, protected storage, account-change detection and resource pagination remain intact.
  • Focused checks and npm run check pass on the new candidate; package/native results are attributed to their exact source and artifact.

Non-goals and risks

No new permission, registration, scope, credential route, dependency, application approval gate or automatic retry. No GitHub repository/Issue/Project mutation is needed for this increment. Do not use a prior-candidate native pass as the new candidate's evidence. Provider/OS consent, the full F-04 operation map, other hosts, signing/notarization, VM qualification, 24-hour soak and Human usability remain separately qualified.

The public registration request adds one bounded read before the native prompt. Network failure must refuse authorization and preserve existing state. Registration can change after that read, so the existing later comparison remains mandatory. The check does not establish that every endpoint is authorized or protect against provider-side changes after the last verified read.
