Issue #54 · Compatible Desktop rollback

9 October 2026. Continue D-24, R-43, NFR-10/NFR-12, F-08 and T-18 within the existing Issue. Final Draft 1.0 requires a prior launchable app and compatible recovery, preserved PM authority, and protection against incompatible databases or replayed external effects. This is agent implementation work; final Human PM Testing remains required.

Evidence and design

The current maintenance journal retains authenticated immutable completion receipts, both exact build identities, the retained app path and filesystem identity, and compatible encrypted backups. Its existing exchange helper verifies parents and swaps the two exact app directories. Startup separately verifies the installed and retained apps, data declarations, real protected stores and custody before clearing the recovery fence. The forward update path requires a newer signed release. No rollback operation currently exists.

Reuse that journal, same exchange helper, idle lease, cancellation checkpoints, native signature verification and startup reconciliation. Rollback selects an exact completed forward update whose installed identity matches the running app. Reverify its retained older app and both filesystem identities. Capture fresh recovery archives of current data, then persist a separate rollback intent referencing the immutable completion receipt. Keep current data when both signed builds declare exactly the same supported formats and Codex CLI version. Preserve PM policy, credential records, release watermarks and external-effect history. No saved worker or external mutation is replayed.

A rollback intent needs a new explicit payload shape. Advance the maintenance database contract to version 3 with an atomic metadata migration that preserves existing encrypted rows and immutable receipts. Signed data declarations advertise version 3. An older version-2 binary is incompatible and cannot be selected; a path or matching version string alone is insufficient. This first implementation supports actual equal-format rollback. Incompatible migration requires guided repair and remains refused.

Ordered work

  1. Add a failing real-filesystem/encrypted-journal rollback regression using the existing completed-update fixture. Native signing and exchange replies may be injected and must remain labeled synthetic.
  2. Add host-only rollback preparation using a completion ID and exact running identity. Validate the retained receipt and native bundles before recording intent. Preserve the original receipt and recovery archives. Reuse replacement and startup reconciliation with explicit rollback validation; forward update version checks remain mandatory.
  3. Bind chat and Settings to an exact expiring rollback preview and the same maintenance lease. Revalidate after every asynchronous boundary. Renderer input carries no bundle path, journal token or qualification flag. Host qualification defaults false until the native effect and restart path pass.
  4. Run meaningful focused checks through admitted external storage, inspect owned cleanup, and run every configured quality command on the final candidate. Regenerate any changed typed fixture recipe before that full run. Native positive rollback, interrupted rollback, exact app/data preservation and final PM journeys require the actual packaged candidate.

Acceptance

Chat and Settings integration uses the existing maintenance preview cards and semantic buttons. “Review Desktop rollback” reads the running packaged build and an unambiguous authenticated completed forward-update receipt under the idle lease. The preview describes a recorded target, not a freshly verified native app. It expires after 15 minutes and binds both build identities, its private completion ID, running bundle and current policy revision. Cancellation, another preview, policy changes or shutdown discard it. “Roll back Desktop” rechecks that exact running build and receipt, then uses the existing native preparation, fresh backup, exchange and restart path. Native rollback qualification remains a separate host-only false default. No publisher connection is needed to inspect the retained local target.

Reuse current typography, spacing, preview cards, status text, keyboard focus recovery and live announcements. Show recorded versions and the consequences first: current saved data and PM settings remain; compatible data and both native apps must pass verification; Desktop closes and restarts after replacement. Expired, missing, ambiguous, incompatible, interrupted, busy and unavailable states preserve data and provide review or recovery as the next action. No new visual system, dependency, configuration setting or approval gate is introduced.

This increment reaches the shared update command parser and IPC shapes, manager dispatch and cancellation, packaged host callbacks, Settings/chat renderer and their focused manager, host and rendered qualification checks. Main-process consumers never accept renderer paths, completion IDs, journal tokens or qualification flags. Focused synthetic checks cover that boundary and exact preview lifecycle; native rendering and actual replacement remain separate required checks.

  • Only a matching authenticated completed forward update can supply a rollback target. Unknown, stale, duplicate, incompatible, changed, missing or untrusted targets refuse before effects.
  • Preparation preserves a durable fence after interruption. Cancellation before exchange preserves the retained app and archives. Once exchange is attempted, failure retains recovery state.
  • Exchange and restart use exact native identities and the selected older build. Startup clears the fence only after both app identities, current protected data and compatible recovery archives are verified.
  • Forward update anti-rollback checks and release watermarks remain unchanged. Older readers refuse the new journal format. Existing pending and completed records survive migration.
  • Chat and Settings expose ordinary review, cancellation and explicit application with preserved PM authority. Unsupported native qualification stays visibly unavailable. Final Human testing uses the built app.

Non-goals and risks

No cross-format downgrade, automatic backup restoration, credential rollback, publisher change, native trust bypass, operating-system permission change, new update source or other-platform claim. A signed same-format declaration is necessary but does not prove the old binary's behavior; actual native testing remains required. Filesystem metadata changes, unavailable native trust, capacity exhaustion, cancellation, persistence failure or failed startup must preserve recovery. Retained app/backup ownership does not authorize unrelated deletion.

Verification

Record source/tree, actual outputs, substitutions, cleanup and not-run checks. The native runner repair is separately active; its inert authentication pass does not qualify rollback or the full suite.
