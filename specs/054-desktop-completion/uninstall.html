First increment: protected credential removal

Reuse the existing private SQLite vault, authenticated connection envelopes, generation fencing, standard crypto and canonical JSON. Return only connection counts and an opaque snapshot digest; never return credentials, raw ciphertext, endpoints or the data key. Bind the digest to identity, generation and exact ciphertext so a same-generation save invalidates it. Bound inventory reads to 2,048 rows, 8 MiB total ciphertext and the existing per-record byte limit. These are admission ceilings, not permission to discard excess records; larger inventories refuse without mutation and require measured qualification before raising the ceilings.

Check the supplied exact snapshot inside BEGIN IMMEDIATE. Authenticate each saved envelope before clearing any row. Increment every persisted connection generation and set its payload to NULL in one transaction. A malformed identity, epoch overflow, corruption, stale snapshot or failed write refuses and rolls back. Verify the resulting inventory before committing. If rollback itself fails, close the vault, wipe its in-memory key and deny later access; do not report completion or infer a recovered transaction. Keep the wrapped key unchanged so local records remain readable. This API is host-only; the uninstall coordinator must first hold the idle fence, settle leases/logout and persist its intent. This increment enables no renderer action, service mutation, app removal or remote revocation. Logical removal and generation fencing do not prove forensic erasure from storage media or prior external copies.

Second increment: settle provider turns before shutdown

The existing connection-manager close aborts leases and waits for connection tasks, but does not wait for already dispatched provider turns. Trace: app shutdown closes development and workspace managers, then the connection manager, then the vault. An aborted provider promise can still be running when close returns. Track completion of actual dispatched turns and await their settlement during close; retain the existing generation and cancellation checks, deny new work immediately, and do not interpret abortion as completion. A caller closing its lease must not remove an unsettled turn from this fence. The regression holds two synthetic provider turns, closes one caller lease, checks that shutdown still waits for both, then releases them and verifies rejected late results and unchanged credential state. Native provider cancellation and the durable uninstall coordinator remain separate qualification work.

Third increment: durable intent and interrupted credential erasure

Before erasing connection payloads, capture both the authenticated current inventory and its exact expected post-removal inventory. The predicted digest binds the retained wrapped key, every identity, incremented generation and NULL payload. This closes the crash window between vault commit and journal update: recovery recognizes only the captured before or after state, and refuses any changed inventory. Keep the existing per-record, aggregate and row limits.

Add one bounded private uninstall.sqlite journal using the existing protected-record codec in its Desktop maintenance domain and a distinct uninstall_state binding. Reuse the native build-identity validator, canonical JSON, SQLite transactions and file-ownership checks. Store only the exact bundle/build/team/custody, credential before/after digests, native service snapshot and preserved-record inventory digest; no credentials or account data. Keep one active intent and the latest terminal receipt, with a 1 MiB database ceiling and 16 KiB encrypted row ceiling. This is a deliberate bounded record, not unbounded uninstall history.

The ordered durable phases are logout-pending, service-pending, credentials-pending, trash-pending and removed. Begin records intent before any effect. Only the current private host token can advance one phase at a time; reopening loses token authority. Exact-snapshot recovery explicitly claims a fresh token and validates the credential state for that phase. It dispatches no effect. The native coordinator must hold the existing idle fence, authenticate the PM action and independently verify logout, service removal, credential erasure and scoped Trash before each advance. The journal alone proves recorded intent, not any native effect. There is no cancellation API that can discard uncertain effects.

Use DELETE journaling, synchronous EXTRA, memory temp storage and transaction rollback. Verify saved state before commit. A rollback failure closes journal access and leaves the recovery fence denied. Future schema, malformed/tampered envelopes, noncanonical ownership, wrong row metadata, stale handles, changed credential state or a failed write refuse without clearing pending intent. Add the journal to the existing managed-data inventory, explicit package inputs and data-compatibility declaration. Open it before normal app work; pending or unreadable journal keeps execution and mutations denied through the existing host-wide maintenance fence. No uninstall button, renderer authority or native effect is enabled by this increment.
