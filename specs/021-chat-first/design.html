Chat-First Desktop prototype

D-06. Final Draft 1.0 product baseline. This document governs a simulated, runnable Mac prototype; it does not qualify product runtime.

PM task and outcome

A PM opens Pipeliner, sees the selected repository and current work, describes a desired outcome in chat, and can inspect Settings or evidence without learning commands. This Issue tests whether the visual and interaction model makes eight core journeys and fifteen Settings categories understandable. The prototype contains only synthetic state and never claims a live action.

The shell probe remains a diagnostic. The new prototype is a separate Electron entrypoint. Its copy identifies every simulated action. No account, GitHub repository, policy, Issue, worker or application service is connected.

Authority and requirement map

The finalized PRD's R-34/R-35/R-37/R-39 require ordinary chat paths, clear target/scope, correction and truthful status. NFR-25–NFR-30 require an original design, conversation priority, all states, nontechnical tasks and preserved authority. F-09 and T-12/T-16/T-17 define later observed UX and trust evidence. The UX companion defines J-01–J-08 and S-01–S-15. Prototype interaction cannot satisfy those runtime tests; D-10–D-26 own real behavior and final usability evidence.

Fixed contract: PM owns Settings/pipeline/autonomy/permissions; Fully Autonomous has zero Pipeliner approval gates; mandatory provider/OS controls remain; one active Issue/Dev per repository; Codex uses managed ChatGPT OAuth; Ollama uses Cloud API keys; background is off; roadmap is absent from app assets.

Visual direction

Use a calm workbench, not a metrics dashboard. A narrow repository rail anchors scope. Conversation has the largest region. An optional evidence drawer follows the selected work item. A thin activity line distinguishes proposed, PM-decided, working and verified results by both label and shape. Use system type to fit the Mac; 4 px spacing increments; comfortable 16 px body text; restrained teal for work, indigo for PM decisions, amber for blocked state, and neutral surfaces for evidence. A compact Pipeliner mark is original CSS geometry, with no copied assets or font licensing dependency.

Semantic tokens cover canvas, raised surface, text, subdued text, border, work, decision, warning, danger and focus in light/dark. Minimum contrast is checked in rendered states. Controls have 44 px preferred targets, visible focus, hover/pressed/disabled states, and no meaning conveyed by hue alone. Motion is limited to opacity/position feedback and removed under reduced motion. At narrow width the rail and evidence drawer collapse behind named controls; conversation and status remain available.

Screen hierarchy and components

  1. Header: Pipeliner identity, explicit “Prototype” label, selected repository, connection summary and Background Off.
  2. Repository rail: synthetic repository choices; switching changes draft target only after explicit selection. Include Settings entry.
  3. Work header: selected Issue, stage, current candidate state, blocker and next action. Show “No active Issue” when empty.
  4. Conversation: PM messages, Pipeliner proposal/status/result cards, exact scope chips and simple prompt examples. The composer supports plain text for rehearsal; unknown text gets an honest prototype response.
  5. Action region: guided choices for eight journeys. A proposal has Before/After, target, effect timing and Apply/Discard. Apply changes only in-memory prototype state and says so.
  6. Evidence drawer: current simulated source, checks, findings, app testing steps and limits. Close/open without losing draft or focus.
  7. Settings: scope selector and fifteen categories. Each category shows effective value, source, default, consequence, timing and either a disabled unavailable control or a rehearsal proposal. Host-only categories have no fake repository override.

Implementation plan and ordered tasks

  1. Keep D-01 probe unchanged. Add desktop/prototype with an Electron main entrypoint, strict custom protocol, CSP, no preload/IPC, no network/permission/navigation access, and task-owned user data.
  2. Build semantic HTML/CSS for workbench, chat, evidence and Settings. Store only synthetic in-memory state. Add local journey cards and proposal review; unknown input gets a truthful simulation limit.
  3. Add one focused interaction test that catches wrong-target/stale Apply and checks all journey/Settings entries. Add a native qualification mode for window, renderer, accessibility and screenshots only if needed to verify this Issue.
  4. Run native Mac walkthrough at wide/narrow and 150% scale, light/dark, keyboard and reduced motion. Review/fix high-impact findings; record VoiceOver tested or pending.
  5. Run configured npm run check, inspect PR checks and exact tree, clean owned processes/data, and publish findings. Intermediate Issue integration follows the PM's 2026-09-29 direction without claiming Human PM QA.

Acceptance and checks

  • All eight journeys and fifteen categories are discoverable; prototype labels stay visible in every result.
  • No real effect path, credential field in chat, roadmap asset, hidden autonomy approval or background enablement exists.
  • Wrong-target/stale proposal is rejected; only a direct in-prototype Apply can change synthetic state.
  • Keyboard, focus, text reflow, accessibility tree, renderer restrictions and current-Mac native window are observed.
  • Run node --test desktop/prototype/*.test.mjs, npm run check, native Electron qualification, and inspect generated package/file list if packaging is used. Record passed, failed and not-run honestly.

Non-goals and risks

No production chat interpretation, GitHub/provider connection, policy store, worker, scheduler, packaged installer, cross-platform qualification or final five-participant study. A polished simulation can mislead the PM; persistent “Prototype” and explicit simulated results mitigate this. In-memory Apply can be mistaken for authority; it has no runtime bridge and resets on restart. Native Electron still needs observed security/AX checks. The finalized planning docs are user-owned in the original checkout and are not copied into app assets.

Observed current-Mac review

macOS 26.5.2 (25F84), arm64; Electron 44.4.5 with Node 24.21.0 and Chromium 152.0.7977.130. The pinned dependency installed locally with zero reported npm audit vulnerabilities. The native qualification finished with 15 passing checks: visible window, renderer restrictions, native Settings shortcut, eight simulated task paths, fifteen Settings categories, ordinary-language search, wrong-target proposal denial, pending-proposal preservation, repository-scoped chat/evidence, keyboard Tab, CSP/network/popup denial, 620 × 700 window at 150% scale without horizontal overflow, narrow-drawer keyboard/focus behavior, and accessibility-tree names. The 1280 × 860 dark and light captures and narrow capture were visually inspected.

Review found stale Issue #42 evidence after switching to Field Notes, an evidence drawer covering the narrow view, proposal replacement after navigating Settings, and keyboard access behind the narrow drawer. These were fixed and the native qualification rerun. Sampled foreground/background token contrast ratios ranged from 4.8:1 to 15.73:1; this is not a full criterion-by-criterion accessibility audit. VoiceOver, uncoached PM tasks, five-participant usability, Windows/Linux, product security boundaries, provider connections and a packaged installer were not run or qualified by this Issue. The prototype uses no preload or IPC and all displayed data is synthetic. Temporary Electron user data and the process were absent after the final qualification run.
