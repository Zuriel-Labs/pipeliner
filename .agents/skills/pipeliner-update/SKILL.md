# Update Pipeliner

Apply the shared [installed repository home](../pipeliner-maintain/references/home.md) and [message-only questions](../pipeliner-maintain/references/questions.md) contracts. First adoption retains its explicit-target gate. When an answer is needed, ask in the final ordinary message and end the turn immediately; no work or tool calls follow until the Human replies.

Use for a requested update to an existing adoption. First-time installation or repository creation uses `pipeliner-adopt`; edits to the upstream framework itself use `pipeliner-maintain`. Monitoring alone uses `pipeliner-monitor-updates` and does not authorize installation.

No PM Testing is required for adoption or updates. Complete the configured suites and agent testing, remediate findings, rerun affected checks, verify publication and cleanup, then report the result. Do not request PM testing, PM acceptance, or a bootstrap-completion approval; future application PM gates remain configured for product work.

Read the target's `AGENTS.md`, `pipeliner.config.json`, Git state, existing repository controls, and [upstream identity and provenance](references/upstream.md). This is direct framework maintenance: do not create or require a GitHub Issue, reserve the active slot, move Project cards, or request Issue-creation/completion approval. Report the target repository and update revision under the explicit maintenance exception in `AGENTS.md`.

1. Resolve the installed own repository home through the shared home contract; require a target only if no verifiable installation exists or an explicit target conflicts. Verify checkout and fetch/push remote identity. Preserve unknown edits and unrelated active work; use an isolated checkout when needed. Another active Issue does not consume permission for this maintenance operation, but overlapping changes must be reconciled without overwriting that work.
2. Resolve and fetch the authoritative upstream into a task-owned source checkout. Pin the requested revision, or the verified default-branch head when the user requests latest, to a full commit SHA. Read that revision's instructions and migration notes before executing its tooling. Keep this checkout separate from the adopter; never merge upstream Git history into the application.
3. Establish the last applied revision from verified provenance or repository history. If unknown, state it; compare installed content against the pinned source without inventing a version. Review upstream changes since the applied revision when available, all managed-file differences, deprecated files, profile compatibility, and changes to quality or release contracts. An identical upstream SHA does not prove a customized adopter is aligned.
4. Plan the requested maintenance update without an Issue branch or Issue gate. Keep the target's repository/Project identity, quality commands, QA topology, release settings, approval phrases, credentials, and stronger custom policies. Ask only for unresolved material changes. Legacy QA missing explicit participants or circulating mode requires the [conditional discovery and explicit migration](../pipeliner-adopt/references/discovery.md) before applying the update. Preserve saved answers; optional cycle topology must be explicitly resolved. Never replace the target profile with an upstream example. When reconciling older instructions, retain the explicit no-Issue exception for these two operational skills rather than routing them back to Issue creation.
5. From the pinned source checkout, run `scripts/adopt.mjs` with the absolute target path and target-owned profile using `--dry-run`. The adopter need not contain this installer. Follow [reconciliation](../pipeliner-adopt/references/reconciliation.md): merge reviewed conflicts deliberately and refresh source/target digests only after semantic review. Inventory removed upstream files separately; do not delete customized or unknown files merely because upstream removed them. Repeat the preview, then apply the conflict-free plan.
6. Validate installed canonical skills, provider links, profile, target quality gates, and relevant live configuration. Preserve target-native commands instead of copying upstream package scripts; verify Node.js 22+ for installed tools and the reviewed-source installer route. Reconcile agent-led continuation, message-only questions with indefinite waits, resumed/merged review, and pre-release versus final identity without weakening custom gates. Questions use only clearly marked ordinary messages; no timers or inferred answers. Audit the target Project's identity/mapped fields/visibility with complete pages. Inspect any changed workflow command chains and refresh only reviewed CI evidence; application builds remain local. Verify intended additions and any separately authorized removals, preserved customizations, and repeat-adoption behavior. Perform agent testing of the installed workflow as well as the configured suites. If validation or agent testing fails, remediate within this maintenance operation and rerun affected checks until clean; do not record a successful update or overwrite unrelated work to recover.
7. Record the applied upstream provenance as described in the reference once reconciliation and local verification succeed. Commit only intended files and publish the verified update to the target's default branch. Use a supporting maintenance branch/PR when existing repository controls require one, without creating an Issue or inventing an Issue reference. Wait for required checks and verify the exact destination revision and content. A local commit or open PR alone is not a published update. Do not bypass branch protections or required external review; report an actual blocked control, not an invented Issue approval gate.
8. Report the target repository's result with old/unknown and new upstream SHAs, target candidate identity, material changes, retained exceptions, verification, and limitations. Report agent testing of installed routing and skills, preserved local configuration, and workflow execution without unintended deployment or scheduling, including findings remediated and checks rerun. Do not hand these tests to the PM or wait for PM acceptance. Do not request an Issue-completion phrase. Remove task-owned source checkouts and temporary validation resources and verify cleanup.

An update request authorizes the framework update and its publication, not a monitoring automation, application deployment, weakened controls, or changes to unrelated Issues.
