# Adopt Pipeliner

Apply the shared [installed repository home](../pipeliner-maintain/references/home.md) and [message-only questions](../pipeliner-maintain/references/questions.md) contracts. First adoption retains its explicit-target gate. When an answer is needed, ask in the final ordinary message and end the turn immediately; no work or tool calls follow until the Human replies.

No PM Testing is required for adoption or updates. The agent owns test suites, agent testing, remediation, verification, publication readback, and cleanup. Do not request a PM test session, PM Testing checklist, or bootstrap-completion approval. Configure application PM gates for future product work without applying them to bootstrap; material-choice clarification and existing repository protections still apply.

For an existing adoption's upstream update, use [pipeliner-update](../pipeliner-update/SKILL.md). First installation and repository creation stay here. Scheduling update detection requires an explicit user request and [pipeliner-monitor-updates](../pipeliner-monitor-updates/SKILL.md); never schedule it as an adoption default.

Install and verify the [Issue-based communication contract](../../../AGENTS.md#issue-based-communication) in the target's `AGENTS.md` and canonical skills, including reconciled files. Status, handoffs, and approval acknowledgments must lead with the owning Issue; linked pull requests remain supporting evidence. Set all future approval phrases to exactly `Approved`; identify the Issue, Human, candidate, gate and authorized outcome in the request. Preserve gate scope and historical evidence. If adoption has no Issue yet, state that without inventing a number; the adoption exception does not require an Issue.

## Target repository location gate

The target repository location is required for an existing repository. Accept an absolute local checkout path, GitHub `OWNER/REPO`, GitHub repository URL, or an explicit statement that the current repository is the target. Explicit new-repository intent starts the creation interview below.

If the request identifies neither target nor creation intent, ask one concise question: `What is the target repository location, or do you want to create a new repository?` Then wait before target or Project mutation. Do not infer a target from the current directory, recent repositories, memory, or an unrelated open task.

For a new repository, ask only for missing name, purpose, owner, explicit visibility and local destination. Confirm the requested creation scope before mutation. Verify authentication, owner access and absence independently: an inaccessible private repository may look absent. A failed lookup, ambiguous 404, network error or permission failure is blocked discovery, never permission to create. Use `intakeDecision` in `scripts/lib/intake.mjs` to check the resolved decision inputs; it does not perform the live probes. Inspect the destination for existing files and Git state and preserve them. Use `gh repo create` with the explicit owner/name and visibility, initialize a purpose-appropriate README, clone or connect the authorized local destination, then verify `gh repo view`, Git root, remote and default branch. If creation fails or readback disagrees, stop and diagnose; do not retry under another owner or visibility.

When a local path is supplied, resolve its Git root and verify its remote identity. When a GitHub identity or URL is supplied, use `gh repo view` to verify it, prefer an existing known checkout, and otherwise create an isolated safe checkout. Report the exact checkout used. Stop and clarify if local and remote identities disagree.

## Autonomous adoption workflow

Read the target repository's complete instructions, current Git state, build/test commands, release topology, and GitHub Project before proposing changes. Own the complete autonomous adoption workflow: resolve identity, create the profile, dry-run, reconcile conflicts, align the GitHub Project, validate, read back, perform agent testing, remediate findings, and rerun affected checks.

1. Confirm scope and identity. Record the exact target checkout, GitHub `OWNER/REPO`, default branch, repository visibility, clean or dirty state, and applicable instruction files. Preserve every unknown change.
2. Inventory existing `AGENTS.md`, provider files, skills, workflows, Issue templates, quality commands, release procedures, environments, labels, branch protections, and Project configuration.
   Branch protection and rulesets are never enabled by default. Ask whether the PM wants branch protection, explaining optional enforced reviews/checks versus agent-managed gates. Record the explicit choice as `workflow.branchProtection` (`enabled` or `disabled`). Missing choice preserves live controls and requires a question; examples and `quality.requiredChecks` never imply consent. If enabled, clarify branch scope and exact rules before configuring them. If disabled, leave new repositories unprotected; remove existing protection only when the PM explicitly requests removal. Use `branchProtectionDecision` for this decision gate, inspect applicable rulesets too, and read every authorized change back.
3. Follow the target's existing Issue, branch, and pull-request governance. If none exists, use a focused branch and pull request for the bootstrap unless the PM explicitly authorizes another supported path.
4. Follow the [conditional checklist and explicit legacy migration](references/discovery.md), reusing saved answers. Resolve the adoption profile from repository and live GitHub evidence. Interview only for unresolved application type, runtime OS/architectures, developer roster and available environments, ordered required QA turns and PM owner, compatible hosts, setup dependencies, ports, fixtures, teardown, release destinations, approval gates and rollback authority. Use only clearly marked message questions; preserve answers and wait indefinitely without timers, reminders or inferred topology. Two developers can share an OS; one can cover several environments.
5. Create a valid `pipeliner.config.json` with explicit Agent Dev/Human PM pairs, accountable GitHub logins, `qa.pms`, `qa.mode=circulating` and complete `qa`, using the four `blueprints/qa` examples as starting shapes. Replace every example identity and command with verified target values. QA topology is independent of release strategy; ask whether release is direct Production, approved review promotion, native or none. Do not manufacture staging or confuse a different product's staging path with this target. Version 1 profiles without `qa` remain readable, but adoption requires discovery; Use reviewed migration tooling with explicitly resolved fields; legacy readability does not supply new participants or approvals. Include the full suite per environment, not a subset justified by another host's pass.
6. Run `node scripts/adopt.mjs --target <absolute-target> --config <absolute-config> --dry-run` from a reviewed Pipeliner revision. Review every create, identical, and conflict result.
7. Reconcile conflicts deliberately. Merge the Pipeliner contract into stronger repository-specific instructions rather than replacing them. Follow [reconciliation and CI review](references/reconciliation.md): preserve reviewed target bytes with a source-and-target digest manifest passed using `--reconciliation`. Never weaken a policy to obtain byte equality. Repeat the dry-run until conflicts are resolved; validate merged semantics as well as hashes.
8. Run the adoption command without `--dry-run` from the reviewed upstream source checkout. Add project-native commands, boundaries, and release detail that the generic contract cannot infer. The installer is not installed into adopters. Keep AGENTS.md stack-neutral, use quality.commands and QA configuration, and verify Node.js 22+ for installed framework tools independently of application language. Do not invent npm scripts in a non-Node target. Classify preReleaseIdentity versus final candidateIdentity explicitly and retain stronger approval evidence.
9. Copy or reconstruct the GitHub Project from `blueprints/github-project.json`, link the target repository, align the label taxonomy, configure supported automations and auto-add filters, and read back fields, views, workflows, linkage, visibility, and labels. Keep merge-driven completion disabled. The blueprint workingExample is attribution, never target identity or a public-visibility default. Use profile field mappings, verify user/organization owner, and record intended Project visibility in project.visibility; omitted legacy visibility is observed and preserved. Run the target-configured paginated audit and separately inspect active cards and workflow trigger settings.
10. Audit every target Actions command chain, including setup/install hooks, local/composite actions, reusable workflows and container definitions. Move application/native/image builds to compatible local suites; preserve lightweight security and contract checks. Remove obsolete arbitrary reusable command inputs and align callers and branch protections through the target's governance. Unresolved chains block publication. Record the reviewed workflow and transitive local file digests in `.agents/ci-review.json`; run validation to detect drift. This review ledger is not a proof that arbitrary shell code is safe. Validate provider imports and regular-file adapters, run every configured local test gate, and perform agent testing of installation, routing, preserved configuration, and repeat adoption. Remediate all findings and rerun affected checks until clean; verify cleanup after success and failure. Use the setup, suite and teardown guidance in [local QA execution](../pipeliner-work-issue/references/local-qa.md), but do not start its application PM turns or retain resources for bootstrap PM Testing. Missing hosts needed for agent checks remain pending, never represented by fabricated results.
11. After local verification, record the verified framework source and full applied SHA using [upstream provenance](../pipeliner-update/references/upstream.md); never copy the source repository's own provenance into the adopter. Commit only intended target files, push the focused branch, and create or update the governed pull request. Read back the exact branch, commit, tree, pull request, checks, Issue, and Project state.
12. Verify the published default-branch revision and installed files, required checks, and cleanup before reporting bootstrap complete. Report what was installed, resolved configuration, exact revision, test and agent-testing results, remediation, and any actual limitations. Do not wait for PM Testing or a bootstrap-completion phrase. An open PR alone is not published completion; preserve required repository review controls and report actual blockers. Bootstrap never deploys the target application.

Adoption authorizes only the target repository and Project placed in scope. It does not authorize application deployment, destructive migration, credential changes, or unrelated backlog mutation.
