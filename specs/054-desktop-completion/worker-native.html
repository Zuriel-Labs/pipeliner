Issue #54 — native Linux worker qualification

Focused engineering evidence for D-21/D-22/D-27, R-25, NFR-09/NFR-11/NFR-14/NFR-16, F-10 and T-03/T-09/T-14. Reuse the actual restricted worker API and the existing custom-command qualification. This increment does not change PM concurrency, the one active Issue/Dev rule, provider authority or the agreed workload.

Evidence and affected flow

The existing qualification creates its fixture in a fixed internal temporary directory and suppresses its failure detail. The worker API already creates one private Lima environment, verifies its pinned Linux disk and image, restricts containers and owns teardown. Current source now passes TMPDIR into that existing private scope. Installed Lima resolves to 2.2.1 and qemu-img to 11.1.2.

Reviewed Lima directories, downloads and caches, VZ attachments, disk conversion, qemu-img output arguments and host-agent resources. Cooperating tool output uses the private tool home/state, caller temporary scope or explicitly selected disk/attachment paths. The Linux EFI path does not call the separate Mac restore installer. This is producer inspection, not a universal native-service containment or OS sandbox claim. Stop the affected run if an unsupported output is found.

Ordered implementation and verification

  1. Use the existing caller-owned qualification context and clean source/tree verification. Create one fresh private fixture, capture its ownership and keep evidence outside the fixture.
  2. Preserve the three existing real custom-command assertions. Capture failure stage and safe error identifiers; retain bounded native diagnostics locally before teardown if needed.
  3. Create five synthetic, distinctly bound repository/workspace manifests through the real API. Verify all five restricted containers are running. Execute five bounded commands concurrently, each reporting readiness before a typed release file. Verify every command is ready together and reads only its own seeded value. Record elapsed time, native process observations and exact image/disk/configuration identity.
  4. Await every command, including failures, before cleanup. Remove only the recorded containers and workspaces. Verify idle inventory, stop/delete only the private VM, then verify owned helper PIDs and file handles are absent before removing that fixture. Retain evidence and any resource whose cleanup cannot be verified.
  5. Run npm run check on the committed candidate. Run node scripts/desktop-tool-worker.mjs on the compatible local Mac with caller-selected output paths. Inspect real logs, exit status, restrictions, measurements and teardown. Do not rerun an unchanged failure.

Acceptance criteria

A dirty source, missing/private-path mismatch or incompatible host refuses before native provisioning. No host mount, forwarded key/agent or renderer access is added. The original typed-input injection and temporary-input cleanup checks pass through the actual runtime. Five distinct bounded commands reach readiness concurrently; their values and process identities remain scoped. Every native result is tied to the exact clean source/tree. Success requires verified removal of owned containers, guest workspaces, VM, helper processes and fixture. A failure records the exact stage and keeps uncertain resources.

Risks and non-goals

The existing 1 GiB VM and five 256 MiB container limits may reveal memory contention; preserve configuration until measurements justify a separate change. Provisioning depends on pinned downloads and the installed toolchain. The API's existing per-command bounds remain; add no overall task deadline. Manual cancellation waits for current provisioning settlement and then performs owned teardown.

This proves the tested worker mechanism only. It does not prove five full PM-authorized Development runs, 25 live repository connections, provider/MCP qualification, Mac guest app testing, native update installation, Human usability, assistive technology, a 24-hour soak or Windows/Linux host compatibility. Those acceptance protocols remain pending.
