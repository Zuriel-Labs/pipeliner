Issue #54 — verified installer staging

This implements the next bounded part of D-24, S-14, R-43, NFR-10/NFR-12, F-08 and T-18. The full outcome still includes native trust, explicit idle installation, compatible migration/rollback and scoped uninstall. A staged checksum is not evidence that those functions work.

Research and decision

Electron's updater API downloads an available update during its availability check and applies a downloaded update on a subsequent launch. Those semantics do not satisfy the agreed separate availability/download/install controls without additional qualification. Keep the existing signed metadata/history path. Implement an explicit host-only byte stage before the native installer. Use Node's existing async stream consumption and file-handle writes for backpressure and partial-write handling; no new dependency. These technical choices remain provisional until executed on the current candidate. Apple's notarization requirements remain separate mandatory native controls.

Specification and ordered plan

  1. Write one synthetic transport/storage regression before the implementation. Use real protected update history and an ephemeral signed publisher; qualify success, refusal, byte tampering, oversize/truncation, redirects/compression, private DNS, abort, stale authority, expiry and altered output ownership. Run only through admitted external storage.
  2. Accept only a trusted host history handle, exact source/current host context, a private canonical destination, explicit byte/free-space budgets, cancellation and an authority callback. No renderer URL, release, file path or qualification flag. Snapshot the freshly authenticated newer release from history. Reject absent/expired metadata, unsupported host, insufficient capacity or stale authority before dispatch.
  3. Reuse public-address and canonical endpoint checks. Resolve and pin one public address; keep TLS validation and reject redirects, compressed bodies and unexpected content types/lengths. Never send provider credentials or cookies. Stream into a uniquely created 0600 file under the exact owned 0700 directory. Hash actual written bytes, handle partial writes and enforce the signed byte ceiling before each write. Request and storage timeouts remain bounded; the host supplies a 100–1,800,000 ms deadline. This ceiling is provisional, not a measured download performance result.
  4. Await response/request/socket settlement, fsync the file, read back its checksum and verify unchanged ownership. Retain the verified file timestamps; after the signed-history refresh and directory fsync, check them again before exposing the host-only receipt. Refuse a same-inode, same-size rewrite after checksum verification. On failure remove only the original, unchanged owned partial file; preserve a replaced/altered path and return a fixed repair error. Close file/directory handles on every path. Preserve unrelated files and protected history. The installer must independently verify the stage before consuming it; a receipt does not prevent subsequent account-owner changes.
  5. After admitted focused and full checks pass, integrate staging into the explicit installation flow. Native Developer ID/notarization, idle-effect fencing, durable maintenance intent, compatible backup, replacement/relaunch, recovery and uninstall require their own implementation and actual T-18 evidence. Do not enable download from availability polling or label a byte stage as an install.

Acceptance and non-goals

The stage returns only after an authenticated available release matches the exact stored bytes/checksum, source history remains unchanged, authority remains current, and owned transport/writer handles settle. Every refusal preserves history and unrelated files. Cancellation waits for settlement and checks cleanup. The stage does not execute, mount, install, restart or publish anything; it does not change policy, service registration, keys or source trust. It remains outside packaged runtime inputs until an actual installer consumer is integrated.

Risks and verification

A checksum does not establish native binary trust. Retained source watermarks cannot be reset to admit a download. The 8 GiB signed asset ceiling is already enforced by the manifest; the supplied host byte budget may be lower. Filesystem metadata guards follow the existing protected-store pattern; this is not OS confinement against a user with control of the account. Interrupted or modified files remain held for recovery when ownership/content cannot be verified. Public TLS, real download throughput, power-loss and installer/migration behavior remain unqualified.

Focused command: node --test desktop/updates/stage.test.mjs desktop/updates/history.test.mjs desktop/updates/source.test.mjs desktop/updates/manifest.test.mjs. Full gate: npm run check. Generated fixtures/logs/caches use the admitted unique external run. Record results against the exact source in Issue #54. A focused synthetic-transport pass does not establish native download, installation, application-build or full-suite qualification.

Native trust and signed build identity — next implementation increment

Keep the same D-24 mappings. The local review builder currently records source/tree outside the app. Add a small canonical build identity resource before signing, so an installer can compare the signed bundle's version, host, source commit and tree with authenticated release metadata. Do not treat a development signature as distribution authority.

Apple's TN3127 defines Developer ID issuer/leaf certificate extensions and the Team ID constraint. TN2206 requires strict recursive signature verification and explains why bundles must remain unchanged after signing. Apple's trusted execution guidance recommends syspolicy_check distribution; the current Mac's manual states that it combines Gatekeeper, XProtect and related checks. A system assessment is separate from actual quarantined first launch and Human consent.

  1. Implement canonical build identity validation and bounded, unchanged regular-file reads. Add real-filesystem regressions for altered, linked, malformed and foreign identities.
  2. Implement one host-only Mac bundle verifier. Accept a canonical app bundle, a pinned publisher Team ID and authenticated release metadata. Require the fixed Pipeliner bundle identifier, Apple Developer ID issuer and application certificate, matching Team ID, hardened runtime, secure signing timestamp, no debugging/library-validation bypass entitlements, an arm64 executable and a successful current-Mac distribution assessment. Compare the signed build identity with the expected version/source/tree/host. Repeat signature/identity checks after assessment. Use fixed native commands with bounded output/time, cancellation and awaited settlement; never execute candidate code.
  3. Write a synthetic native-command regression before implementation. Exercise exact command arguments, refusal of development/wrong-team/invalid signatures, missing timestamp/runtime, policy denial, non-arm64 content, stale identity, cancellation and replaced files. Label mocked native responses explicitly. Run the real verifier against a retained Apple Development review app to prove refusal if an owned current artifact is available; a Developer ID/notarized positive case remains pending its actual credential/artifact prerequisites.
  4. Embed the identity resource in the existing builder before signing, include its digest in the build record, and preserve existing local-review labeling. Run focused checks, then the configured full suite through its qualified process route. Actual signed build/native installer checks require a compatible admitted run.

This increment verifies bundle trust; it does not mount, install, replace, restart, migrate, roll back, uninstall or publish. These remain required in the full Issue. An unavailable native tool or failed assessment refuses the candidate. No permission, provider, OS control, signature or notarization fallback is introduced. The verifier is current-Mac technical implementation; older Mac and other-host evidence remains pending.

The first actual native requirement probe on 6 October rejected the initial requirement syntax: unexpected token: not. The mocked regression had not established parser compatibility. Use the documented ! negation operator and negated entitlement existence predicates; Apple's requirement language treats a false Boolean value as absent for this test. Keep one shared requirement generator and execute it against the native parser. A successful development-signature refusal is negative evidence only; notarized Developer ID acceptance remains pending. The builder reads back the embedded identity after signing and compares it with the exact source/tree before constructing the review image.
