# Issue #9: paired QA and release cycles

## Outcome and boundaries
One home repository and one Issue execution loop serve simple and staged releases. Devs are Agents; PMs are Humans. Existing 12 skills stay canonical. No adopter update, application deployment, protection change or monitor is authorized here. Bootstrap/update retain their Agent-only acceptance exception. Strict candidate invalidation applies; no evidence-only exception.

## Design
- Keep profile version 1 readable. Add `qa.pms` (id, kind=human), developer kind=agent and accountable `github` login, and `qa.mode=circulating`. New adoption requires these explicit fields; legacy reading stays supported, but discovery precedes any new QA sequence. Every PM/developer/environment has a turn; multiple turns can share a PM.
- Home resolution starts from the installed canonical skill/profile root, validates local Git root, AGENTS.md, profile and fetch/push origin identities using argument-based Git calls. First adoption still requires explicit target. Do not infer auxiliary repos.
- Circulating evidence has candidate, records (historical rounds allowed), owning issue, scope and currentTurn. Each record has a unique positive round per turn; choose the latest record, never fall back to an earlier pass after a failure. Current pair must complete on the current candidate before next stale pair; all pairs must match before complete. Append exact-resource cleanupResolutions for historical rounds rather than changing history. Legacy linear evaluator remains readable for legacy evidence only; operational CLI requires paired migration. New records require a structured Showcase and Agent review evidence as well as suite, PM and cleanup evidence.
- Showcase carries scope=issue/release, issue number, summary, findings array (empty explicitly means none), testResults, target, prerequisites, steps (action/expected), regressions, limitations, nextOutcome, approvalPhrase and candidate. Agent/Human evidence authenticity remains a live-agent responsibility; helpers only validate supplied data.
- Optional `release.cycle` has ordered phases: id, kind=development/stabilization/production, branch, environments, approvalPhrase, readiness criteria, promotion=source/same-artifact/distinct-artifact and forwardPortTo. Phase IDs/branches/environments are explicit. All QA turns and PMs participate in each aggregate release gate. Multiple development Issues belong to one release target/milestone and Release Issue. Status never encodes phases.
- A cycle state records target, releaseIssue, phase, candidate, scope Issues, frozen scope, blockers, QA evidence, PM approvals, verification/rollback evidence and artifact continuity where applicable. Derived releaseScope hashes Release Issue/target/phase/sorted scope and binds every aggregate candidate/evidence record. Non-production uses pre-release identity; production requires final identity, including every phase environment's verification. Artifact digest must agree with candidate and all approvals; immutable Production cannot select distinct artifacts. Pure phase decision returns waiting/ready, never mutates or authenticates. Phase branch routing rejects unknown or frozen feature scope; Beta fixes forward-port to development and require verified integration. Final release acceptance remains distinct from pre-release authorization.
- Message-only questions throughout, indefinite waiting, preserve answers. Related feedback stays on the same Issue; unrelated intake needs exact draft approval. Pausing a Release Issue for a blocker needs PM direction.

## Risks and mitigations
Avoid compatibility silently implying approvals: explicit migration, no invented people or topology. Avoid stale history resurrecting a pass: latest record plus current candidate. Avoid circular gating: build and Agent review before PM approval. Avoid blanket home claims from profiles alone: inspect real Git remotes. Preserve exact-tree merge continuity separately from original QA records. No arbitrary commands execute from validation.

## Acceptance and verification
Follow the complete approved Issue #9 body. Behavioral tests cover message-only waiting, portable/mismatched Git roots, explicit participant coverage, one/two/three pairs, middle/last remediation, missing host/PM/Showcase/cleanup, duplicate rounds and stale evidence, branch routing/freeze/blockers/forward-port, aggregate all-PM approvals, artifact continuity, legacy discovery, installed CLI, fresh/repeated/customized non-Node adoption. Run changed-skill validation and npm run check. Review transitive CI imports before refreshing digests. Report provider documentation checks separately from live provider execution.
