Issue #17 · Mac authority qualification

Pre-code specification · M-0/D-02 · 28 September 2026. This is a bounded current-Mac feasibility experiment under Final Draft 1.0. D-01 established an Electron shell, not a worker boundary. The candidate must preserve the one active Issue, PM-owned controls, Chat-First operation and zero application gates in Fully Autonomous. The roadmap remains outside runtime and packages.

Evidence and decision to test

The current host is macOS 26.5.2 arm64 with Xcode 26.6, Swift 6.3.3 and Node 22.23.2. Apple documents separate App Sandbox/XPC capabilities and security-scoped bookmarks; a directly launched helper inherits its parent's static sandbox and cannot be assumed isolated from it. Electron's Node-enabled utility process has process separation but no established PM boundary. The first diagnostic tested sandbox-exec and an ad-hoc signed App Sandbox helper. Both denied file access, but a read-only Apple Event still reached Finder, including from arbitrary code built inside the allowed workspace. That is a measured authority bypass, so neither process configuration is accepted as the worker boundary. The next experiment uses a separate task-owned Linux VM with no broad host mounts, and a restricted container with only a disposable workspace mount. The VM is a worker boundary candidate on this Mac; host-native build/test must remain a separately qualified broker operation.

Primary sources: Apple sandbox violations, Apple scoped file access, Apple XPC services, Electron utility process, Podman machine configuration, and Podman container restrictions.

Implementation plan

  1. Inventory task-owned fixture paths and processes. Retain the failed native probe as regression evidence; its failures must never become passing tests by being omitted.
  2. Create a dedicated Podman VM whose configuration has no default host mounts and a restricted container with only the disposable selected workspace. Verify actual VM and container mount tables before running adversarial input; reject any broad mount or host socket.
  3. Write one runnable regression check that verifies the positive operation, every adversarial attempt and exact protected before/after bytes; verify descendants, aliases and cleanup. The broker uses fixed operations and targets, never agent-origin PM apply.
  4. Run the prototype on this Mac, capture redacted positive/negative traces, process/VM identity, network and automation effects, and exact limitations. Test one task-owned app launch through the broker only if safely scoped; otherwise record the blocker.
  5. Review the complete diff and all configured checks. Keep critical/high bypasses open for remediation. Prepare a PM-accessible candidate and full Showcase before the sole merge approval.

Acceptance criteria

  1. One permitted workspace write succeeds and exact readback matches; broker rejects non-allowlisted target and operation.
  2. Policy, credential fixture, unrelated workspace, control socket and PM apply decoys remain unchanged after direct, child, alias, Git/hook and IPC attempts. A missing test is not a pass.
  3. Worker receives no live secrets or broad environment; network and automation attempts cannot reach host Finder or obtain a host effect. Capture any OS prompt rather than approving it.
  4. Exact Mac/tool versions, VM/container mounts, process and sandbox mechanism, native signature/entitlement state, effects and limitations are recorded. Failed native profiles remain failed; Mac-native build/test remains provisional until a safe broker path is verified.
  5. Task-owned fixtures/processes are removed; unrelated resources are untouched. npm run check and the configured local-mac suite pass. Failures remain visible.

Non-goals and risks

No provider session, real credential, GitHub mutation, PM UI, pipeline policy store, background service, distribution, Windows or Linux proof. The main risk is mistaking a legacy sandbox diagnostic for a ship-ready boundary. Other risks are path aliasing, descendant escape, accidental TCC prompts, and overly broad system read rules. The runner must fail closed and report each unqualified path. Required future app-test capabilities that cannot meet the boundary remain blockers for their later roadmap Issues; no unrestricted fallback is permitted.
