Ollama Cloud agent loop qualification

Bounded current-Mac feasibility. Final Draft 1.0 remains product authority.

Outcome and evidence boundary

F-03 asks whether direct Ollama Cloud with a bearer key can complete a selected-model, streamed synthetic tool loop and resume from Pipeliner-owned state. The result will classify observed capabilities and blockers. It will not be a product connection, worker isolation proof, or general provider parity claim.

The official Cloud guide fixes the remote endpoint and distinguishes API model names from CLI suffixes. Authentication requires a bearer API key for inference. Streaming uses newline-delimited JSON. Tool calling says to collect complete streamed assistant fields and return tool results in a follow-up. These documents do not prove a particular cloud model or account path.

Requirements and boundaries

R-22 selects Cloud API keys only. R-23 requires capability discovery per model and a truthful zero-gate decision. R-31 requires measurable usage before hard enforcement. NFR-03 protects credentials; NFR-08 forbids unconfigured provider fallback. F-03 and T-07/T-09/T-15 require live and failure evidence. A-05 keeps this adapter separate from Codex OAuth. No key, transcript or secret-bearing error body enters source, Issue, PR, public log, renderer or worker.

Minimal design

  1. A trusted Node.js CLI accepts only fixed https://ollama.com/api/tags and /chat. The key comes from the local process environment. The CLI logs bounded metadata only. No child process or local daemon receives the key. A future product adapter must obtain its key from protected storage; this probe does not qualify storage.
  2. Catalog selection uses exact API names returned by /api/tags. A selected model is recorded with API response shape and observed tools/usage. No inferred CLI-name conversion.
  3. An NDJSON parser decodes UTF-8 across byte boundaries, enforces line and total size limits, requires a terminal done:true, and rejects malformed/incomplete/duplicate terminal output. It gathers complete tool-call objects and assistant text; ambiguous or partial calls cannot pass the broker. It never dispatches a tool while a stream is incomplete.
  4. A tiny broker accepts one synthetic lookup_fixture call only for the exact task target and nonce. It validates argument keys/types, one call, current policy epoch and completed stream. Unknown, duplicate, stale or wrong-target requests return a denial with no effect.
  5. The transcript checkpoint holds only synthetic messages, model name, task target, tool result and outcome marker. Write it atomically with restrictive local mode. On resume, validate schema and already-applied effect identity; send the verified transcript for the final response without re-executing the tool. Missing/uncertain state blocks.
  6. Each remote request has a fixed host, deadline, response bound and small output budget. Cancellation aborts the request and denies later dispatch. Errors report status/class without raw response text or key material. No fallback.

Ordered tasks

  1. Inspect the existing code and official API contract. Capture the exact host and Node versions. Inventory temporary resources. Do not read or print key value.
  2. Write parser, broker and checkpoint tests first: split chunks, malformed line, incomplete stream, unknown/wrong target, duplicate effect, stale checkpoint, abort and transport outage.
  3. Implement the smallest Node stdlib/fetch harness. Discover live catalog and select one candidate by returned name. Keep live requests synthetic and output bounded.
  4. Run valid-key streamed tool request, follow-up/resume, invalid-key, cancellation and safe failure cases. Record raw provider content only in protected transient memory; report sanitized metadata.
  5. Review security/privacy and exact response semantics. Run focused tests, npm run check, current-Mac QA and PR checks. Publish a dark-mode qualification report and clean task-owned resources.

Non-goals and risks

No production key storage/UI, arbitrary hosted API endpoint, local Ollama daemon, real repository mutation, broad model matrix, cross-platform support, worker VM integration, general agent SDK, product budget enforcement or completed app. Live model output may ignore requested tools or omit usage; classify that model accurately rather than fabricating support. Usage and Cloud availability can change; record date, returned model name and API response metadata. A timed-out request may finish remotely after client cancellation, so this probe makes no external effect and local dispatch remains blocked.
