Issue #54 — authenticated update availability

D-24, S-14, R-43, NFR-10/NFR-12, F-08 and T-18 remain the agreed baseline. The current app has an offline signed manifest verifier and channel controls; it cannot read an update source. This increment supplies the missing bounded host reader. Installer delivery, idle installation, migration, compatible rollback and scoped uninstall remain separate required work. No publisher key or production feed is invented.

Evidence and design

The existing Tools HTTPS transport already validates public destinations, resolves all returned addresses, rejects private addresses and pins one validated address for TLS. Reuse that resolution function; leave MCP behavior unchanged. Use Node's standard HTTPS request with its hostname certificate validation, no proxy agent, no credentials, no redirects and no connection reuse. The host supplies the previously trusted Ed25519 key, exact source identity/origin/path and current channel/platform/version/retained sequence. Neither renderer, worker nor received metadata may supply trust. Request only the fixed channel JSON under that source prefix, never the release asset.

Require status 200, application/json, identity encoding, a body of at most 16 KiB and exact declared length when present. Bound DNS, network and completion to one 30-second deadline; propagate cancellation. Destroy the response/request and wait for the actual socket close on success, refusal and abort. Pass the bytes to the existing canonical signed-manifest verifier before returning a release. Retained sequence and availability timestamps must later be durably protected by the host before app activation; this transport neither invents those records nor enables automatic checks.

Ordered work and acceptance

  1. Add a failing bounded reader regression with explicit injected DNS/request objects. Assert the fixed GET destination, address pin, TLS validation and credential-free headers. Valid signature returns the immutable release; redirects, compression, oversize/short bodies, malformed/signature-invalid metadata, wrong DNS family/private destination, timeout, cancellation and interrupted streams refuse.
  2. Export and reuse the existing DNS resolver without changing its native rules. Implement only the bounded reader and close handling with standard Node APIs. Check inputs before dispatch and recheck cancellation after resolution and verification.
  3. Run the focused reader/manifest and existing Tools transport checks through the reviewed managed external launcher. Distinguish injected transport checks from native HTTPS/network qualification. Run the unchanged complete configured quality command once the separately qualified process audit admits it.
  4. Integrate availability with protected retained sequence, host-owned trusted source catalog and chat/Settings in a subsequent verified increment. Keep current production check/install controls unavailable until those prerequisites exist; expose no arbitrary URL, trust-key entry, automatic download/install/restart or background operation.

Verification and risks

Focused command: node --test desktop/updates/source.test.mjs desktop/updates/manifest.test.mjs desktop/tools/transport.test.mjs, with all temporary outputs and caches in the managed external run. Full gate: npm run check. A signature from a compromised publisher can still authorize bad metadata; native binary trust, compatible backup and installation remain mandatory independent gates. Injected transport success proves neither a real publisher nor TLS/native package behavior. Source/sequence changes and cancellation invalidate an in-flight result.

Primary references: installed Node 22.23.2 HTTPS, DNS resolver cancellation, and Electron autoUpdater. Electron's availability call automatically downloads available updates; the agreed availability-only default requires this explicit metadata path. All evidence remains pending before execution.
