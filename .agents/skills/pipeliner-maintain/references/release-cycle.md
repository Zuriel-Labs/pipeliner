# Optional release cycle

Read this reference before selecting a branch, integration target or acceptance gate whenever `release.cycle` is present. Absence preserves the simple Issue loop and configured release strategy. Do not infer a cycle, Alpha/Beta branches, phase names or deployment topology from examples. Cycles orchestrate the same 12 skills; phases never become Project Status values.

## Configuration and state

Phase `kind=production` means the final release stage, not necessarily a service Production destination. With `multi-environment`, it may be native Stable distribution whose configured environments all have `role=native`. Prepare candidates with `pipeliner-release-candidate`, follow configured native distribution/integration authorization and verification through review/close, then require aggregate QA, every Human PM's final phase approval and completion acceptance on the actual Stable identity. Do not invent a Production URL, service deployment ID or Production destination, and do not invoke `pipeliner-release-production` unless an actual `role=production` destination is configured. The four strategies (`none`, `immutable-promotion`, `direct-production`, `multi-environment`) retain their existing meanings.

Each ordered phase explicitly declares its `id`, `kind` (`development`, `stabilization`, `production`), `branch`, `environments`, `approvalPhrase`, `readiness`, `promotion` (`source`, `same-artifact`, `distinct-artifact`) and `forwardPortTo`. At least two phases run from development to final production; development cannot follow stabilization. Stabilization requires nonempty development phase IDs in `forwardPortTo`; development and production require empty arrays. Resolve actual branches, hosts, destinations, required approvals and rollback authority during discovery. Preserve `release.strategy` as the delivery procedure within the selected phase; phase routing takes precedence over simple default-branch assumptions. Incompatible strategy/promotion settings require explicit resolution before mutation. Follow the exact [CLI and evidence format](evidence.md), including `issues`, `frozenIssues`, `records`, `currentTurn`, `approvals`, `verification`, `rollback`, `forwardPorts` and `artifact` state fields.

Use one release target/milestone to group development Issues and a dedicated Release Issue to own aggregate validation and promotion. Create that Issue only through exact draft approval. Record target, Release Issue number, current phase, exact candidate, scope Issues, frozen scope, blockers, aggregate QA, actual PM approvals, verification/rollback evidence and applicable artifact continuity in durable cycle state. Keep phase and milestone linkage separate from Backlog/In Progress/In Review/Done.

Bind every aggregate identity and approval to derived `releaseScope` using `releaseScopeKey(state)` as specified in the evidence reference. Scope binds the Release Issue, target, phase and sorted frozen Issue set, so unchanged source/tree cannot carry approval into a different release scope. Append `cleanupResolutions` to prove later cleanup of exact historical resources; never rewrite QA or PM history.

## Issue integration and scope freeze

Before work, verify the Issue belongs to the release target and resolve its permitted phase branch. Development branches and supporting PRs start from and target that configured branch. Unknown scope blocks routing. Once scope is frozen for stabilization, reject new feature scope; do not silently admit it as a fix. Related findings remain on the owning Issue, while unrelated product intake requires a new exact approved draft. After merge, use a fresh supporting PR from the current owning phase branch, retaining the same Issue and prior evidence.

A development Issue completes after its own latest-candidate paired QA, full Issue Showcase, configured integration acceptance, exact-tree phase integration and readback. Its completion does not assert Production release or accept the aggregate release. Record its contribution under the target/milestone and Release Issue. Do not invoke Production merely to close a development Issue, and do not reuse its approval for a Release Issue. Existing stronger gates remain applicable; ambiguous completion semantics require discovery.

Only one Issue is active by default. A Release Issue waits in Backlog until the slot is available and its work is authorized. If a blocking Issue must become active while the Release Issue is active, ask the Human PM to pause the Release Issue; only the PM may authorize On Hold. Preserve cycle evidence and resume explicitly after the blocker is resolved. Do not create a second active Issue or auto-pause to work around the limit.

## Aggregate phase gate

1. Read the Release Issue, milestone membership, frozen scope, current phase, integration commits and blockers. Verify all scoped contributions and phase readiness criteria; individual Issue passes do not prove the aggregate candidate.
2. Prepare the complete phase candidate on compatible local hosts and perform Agent review before requesting approval. Reuse a verified unchanged artifact when appropriate. Run all configured QA turns and Human PMs against the aggregate latest candidate using [circulating QA](../../pipeliner-work-issue/references/local-qa.md).
3. Present a full [Showcase](../../pipeliner-review-issue/references/pm-testing.md) with `scope=release`, the Release Issue number, all included changes, phase target and unresolved limitations. Every required pair and PM must finish on the latest candidate; a component Issue approval or one PM cannot stand in for aggregate coverage.
4. Require zero unresolved blockers, verified cleanup, all readiness evidence, actual phase approval(s), rollback evidence and required forward-port verification. Revalidate immediately before an authorized transition. Production mutation requires separate configured authorization against pre-release identity; do not wait for final production-phase readiness before deploying or use that final approval as pre-deployment permission. `evaluatePhase` evaluates production only after final identity, aggregate QA and verification exist. Pure helpers neither authenticate evidence nor execute a transition.
5. For non-Production preparation use `pipeliner-release-candidate`; use `pipeliner-review-issue` and `pipeliner-close-issue` for authorized phase integration/continuation. Use `pipeliner-release-production` only when that phase has an actual configured Production destination; native-only Stable follows candidate preparation and configured distribution verification through review/close. Record resulting phase source/tree, artifact and applicable distribution or deployment evidence, then continue the Release Issue to its next real gate. Advancing a phase does not close the Release Issue.
6. Final release PM Testing and exact completion approval cover the verified final release identity. Pre-release phase authorization is not final acceptance. Close the Release Issue only after all phases, scope, forward-ports, verification, cleanup and final acceptance pass.

## Stabilization fixes and artifact continuity

Fix stabilization/Beta findings on the owning phase branch and verify integration into every declared `forwardPortTo` development branch. Record source and destination commits, reviewed diff/tree relationship, conflict resolution and destination checks. An attempted cherry-pick is not verified forward-port completion. Keep the blocker unresolved until integration is proven; do not silently omit a future development branch or overwrite its work.

`source` promotion carries reviewed source with explicit tree continuity; it does not claim binary identity. `same-artifact` promotion must reuse the exact approved immutable artifact without rebuilding. `distinct-artifact` permits explicitly configured platform/environment artifacts, each built locally and independently identified, reviewed, tested and approved; never label different bytes as the same artifact or transfer native-session approval across hosts. An immutable-promotion strategy must retain its same-artifact requirement.

Any candidate change, including included documentation or evidence changes, invalidates prior shared QA: there is no evidence-only exception. Preserve history, finish the current pair on the new candidate, then circulate to the next stale pair. An intended exact-tree merge or same-artifact deployment is a separately verified stage transition: retain original QA candidate records and link resulting source/deployment identities without rewriting history or claiming a new artifact was tested. Unexpected tree, dependency, configuration or artifact changes require fresh QA and approvals.
