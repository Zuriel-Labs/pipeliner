# Message-only questions

The official approval response is exactly `Approved`, case-sensitive, for every gate including Issue creation. Put only that word in the copyable code block. Identify the owning Issue (or exact new-Issue draft), Human PM, gate, candidate and authorized outcome in the surrounding request. Keep one pending approval request per Human in the conversation. Bind the actual response to that request; the same word never authorizes a different candidate, another PM's turn or an unstated future deployment. If the pending request is ambiguous, clarify in a message. Never infer the gate from phrase equality. Historical approvals retain their original wording and scope; do not rewrite them. Bootstrap/update sets all approval phrase fields to `Approved`, preserving distinct evidence and release controls.

Final QA acceptance also authorizes the stated integration, verification, closure and cleanup outcome when no distinct release-stage testing remains. Never append an administrative Issue-completion confirmation. All required pairs must still finish; intermediate approvals advance the baton. See AGENTS.md's one-approval-per-tested-outcome rule.

Ask every clarification as a clearly marked `Question:` in an ordinary agent message. Do not use native question controls, structured question tools, forms, polls, timers or scheduled reminders. This applies to adoption, updates, Issue intake, QA, review, release, completion, health audits and monitor configuration. It does not prohibit using an explicitly authorized scheduler to create the requested monitor.

Explain the material choice and tradeoff; recommend a default only when evidence supports it. Save resolved answers in the target-owned profile or existing durable decision record, with their scope and source. Reuse confirmed answers unless conflicting live evidence or a changed requirement makes them obsolete. Ask only the unresolved conditional questions; do not repeat an interview on resume.

Before asking, save resolved answers and finish necessary evidence recording or task-owned cleanup. Ask in the final ordinary message and end the turn immediately. Stop all work and tool calls for this task after asking, including independent work, background continuation, polling, sleep loops, timers and reminders. Waiting means yielding control to the Human, not keeping an execution running. Resume only after the Human replies, at their own pace. Silence, tool timeouts and elapsed time never supply an answer or approval. If a reply leaves a required choice unresolved, ask only the remaining question and end the turn again. Do not contact another Human PM without explicit messaging authority.

For Codex/ChatGPT, use the final response for questions, not an intermediate progress update or native question tool. Other providers must use their ordinary response mechanism that ends the turn. Availability of a question tool never changes this contract. An approval request follows the same turn boundary.

During adoption/update, inspect effective repository and provider instructions for conflicting question guidance, including target customizations and prompts. The installer's `questionConflicts` identifies known conflicting text before writes, even when a reconciliation manifest accepts its hash. Reconcile only authorized target text, preserve unrelated instructions, regenerate reviewed hashes and rerun the dry-run and validation. Static detection covers known directives, not arbitrary prose or host-injected instructions; manual review remains required. If higher-priority host instructions require incompatible question tools or continuation, explain the specific conflict and its source. Repository instructions cannot override them; do not silently edit global settings or claim the provider was fixed.

Approval requests are messages too: identify the owning Issue, current gate and exact candidate, then give that gate's configured phrase in its own standalone fenced code block. Each separate value the Human must paste gets its own block. An Agent cannot approve for a Human, reinterpret feedback as approval or carry approval to a changed candidate. Adoption/update retain their no-PM-Testing and no-bootstrap-acceptance exception; discovery questions and real repository controls still apply.
