Design brief and flow

Continue the established navy surfaces, mint verified/action accents, lavender PM intent and three-stroke mark. Chat remains the main entry. Add a compact workspace choice/preview beneath the conversation and the equivalent Repositories Settings panel. Keep one setup draft in the foreground: progressive questions identify missing choices; cards show selected target, purpose, Private/Public, folder, Project and planned additions. Use plain language and text status. Advanced node IDs appear only in optional evidence, never as required input.

  1. “Import a project”, “Import OWNER/REPO”, “Use a local project” or “Create a private project” begins a host-owned draft. Ask only unresolved fields; selection buttons and text feed the same validator. Ambiguous or quoted content has no setup effect.
  2. Import existing local: native chooser selects a folder, verify Git identity, match the authorized App catalog, and inspect modified/untracked counts without exposing file contents or changing files. Existing aliases select the one registered workspace. Existing remote import: select the authorized catalog repository and a native destination parent; use a new child folder only.
  3. Create: select a verified personal/organization owner through the separate setup connection; resolve name, purpose and explicit visibility. Recommend Private in guidance but leave the choice unresolved until the PM selects it. Create only from the exact preview. After creation, pause at a truthful installation-access state if the scoped App cannot see it; preserve the created identity and offer fixed App installation/recheck.
  4. Select an existing owner Project or a new private linked Project. Inspect complete fields/options and linked repository identities. Map four governance fields using existing single-select IDs or add a missing field. Desktop Status requires Backlog, On Hold, In Progress, In Review, Pending Review, Done; Priority P0–P3; Impact High/Medium/Low; Effort XS–XL. Preserve every other field/option/card/workflow. Preview any link or additions explicitly.
  5. “Apply this setup” or Apply connects the exact current draft/proposal to direct PM origin. Revalidate connection/local/remote/Project identity and option contents. Persist every effect intent before dispatch and the verified result after readback. Duplicate apply returns its recorded outcome; a changed or uncertain candidate is blocked.
  6. Completion shows remote visibility, local folder, linked Project, verified field mapping, existing work preserved, no Dev assigned/no run started, and background off. Select that workspace for later repository-scoped conversation. No mirrored profile activates runtime policy.
  7. Cancellation and close abort pending operations and wait for owned Git/inspection resources. Keep completed external resources and uncertain intent for recovery; never delete a repository/Project/checkout automatically. Reopening lists pending setup with deliberate readback/continue, never replays.

Data boundary

Credentials remain solely in the D-10 encrypted vault/provider Keychain. Setup database stores selected account/connection references, repository/Project node IDs, local filesystem identity/path, field mappings, proposal fingerprints and effect status in a private 0600 file beneath the 0700 protected app directory; this metadata is plaintext locally and never mounted to execution workers or exported automatically. No source content, raw token, key or provider logs is stored. Conversation persistence/export/retention encryption remains D-25; this Issue does not claim forensic deletion or compromised-host protection.

Risks and controls

  • GitHub App creation/Projects authority differs by owner: use only the qualified supported route, surface missing consent/installation/organization policy, do not synthesize compatibility.
  • Read-then-write races: compare full mapped fields/options/account/repository identities before applying and verify after. Existing option IDs survive. Partial/external drift blocks rather than rewriting unexpected state.
  • Lost reply or restart: durable dispatched/uncertain state blocks repeat effects. Repair only through exact readback/explicit use of an existing result; no inferred absence, auto-create retry or destructive cleanup.
  • Untrusted Git configuration/large working trees: trusted fixed read-only Git commands, bounded output, disabled hooks/includes/helpers, inspection off the main event loop. Unsupported/failed identity remains a repair state.
  • Destination aliases/symlink changes/collisions: native selection, canonical inode/path recheck and exclusive child creation; protected application/system directories excluded. Never use an existing target for clone.
  • Cancel/revocation after a remote effect: preserve recorded result/uncertainty, fence subsequent effects and offer explicit repair. Local cancellation is not remote rollback.
