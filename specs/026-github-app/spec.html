Scoped GitHub App qualification

Final Draft 1.0 remains product authority. This qualification precedes the production connection UI and executor.

Outcome and current evidence

Implement the smallest trusted device client and operation planner that can qualify the designated App against synthetic and authorized live fixtures. Reuse Node fetch, URL, AbortSignal and existing complete Project pagination. No general GitHub SDK, authenticated proxy or workflow engine.

The current engineering CLI has access to the Pipeliner Issue/Project lifecycle. Its App-installation query returned HTTP 403 with a requirement for an App-authorized access token. This rules out treating that CLI connection as App evidence; it does not establish App absence. Public lookup of the candidate slug returned HTTP 404, which is not used to prove registration availability.

Decision update, 1 October 2026: the PM selected the proposed Pipeliner Desktop App under Zuriel-Labs and authorized the two exact new private repository/Project fixtures in the setup plan with “Zuriel Labs, yes.” Resolved choices do not need another administrative approval.

GitHub’s live account-confirmation page blocks access to the registration form until the PM authenticates. Actual App registration, public client ID, installation consent and live permission evidence remain pending. Fixture tests do not satisfy F-04; no native App integration or provider-control bypass is claimed.

Requirements and boundaries

R-03/R-32 require verified Issue/Project/PR/check access and guided connections. R-06 and R-05 protect Ready and all three active statuses. R-26/R-29 require unchanged candidate evidence and distinct integration outcomes. NFR-03/NFR-16 protect secrets and bounded API reads; NFR-17/NFR-18 forbid blind replay and invented readback. F-04 and T-01/T-02/T-09/T-10/T-15 govern actual qualification; S-01 exposes truthful connection capability later.

Only the PM designates the connection and scope. Execution requests receive neither tokens nor a generic API route. Direct PM readiness is a separate authenticated product path; a caller-supplied actor field is never authentication. This Issue's pure planner validates trusted inputs and is not itself an OS or PM-origin isolation proof.

Focused implementation

  1. Device client: accept a nonsecret client ID for the selected App; fixed GitHub OAuth endpoints only; bound response and deadline; reject redirects. Return only the verification destination, display code and expiry to a protected surface. Keep the device code and tokens in trusted memory. Poll no faster than the supplied interval, increase for slow-down, handle denial/expiry/cancellation. Refresh device-issued tokens without a secret. Do not log response bodies or tokens. Do not consult environment credentials, gh auth, existing sessions or a PAT.
  2. Operation planner: exact request keys and trusted repository/Issue/run/policy/epoch identity. Typed operations generate fixed REST paths or constant GraphQL documents with variables. Validate payload keys/types/lengths. Deny Ready changes and protected-label replacement, wrong targets, unknown commands, arbitrary URL/query injection, stale versions/epochs, and stale merge heads. Setup operations use separate PM-origin setup authority rather than execution-worker authority. Check current complete state before mutation.
  3. Readback: require verified repository/node identities and full Project connections via the existing collectConnection helper. HTTP 401/403/404 and GraphQL partial errors remain distinct failures. Preserve uncertainty after a lost write response; never retry a mutation based only on transport failure. The durable product ledger remains D-08.
  4. Live sequence: once the PM selects an App and fixture scope, use provider-owned sign-in through a protected purpose-limited surface. Verify selected installation and effective permissions. Create or use exactly authorized private fixtures; record their IDs locally, run the operation inventory, verify effects and failure cases, then remove only explicitly authorized disposable resources. Do not mutate Pipeliner work items as fixtures.

Acceptance criteria

  • Fixed destinations, no environment/CLI token fallback, no bundled secret/private key, no secret-bearing log, and abort/expiry prevent dispatch.
  • Provider poll interval, slow-down and refresh are followed; tokens remain trusted and device/auth failures are sanitized. All outstanding credential flows terminate on cancellation.
  • Wrong scope, stale epoch/policy/head, unknown tool, Ready changes/replacement and incomplete state produce no mutation. Active statuses are exactly In Progress, In Review and Pending Review.
  • Every operation group has actual authorized personal/organization results or a visible blocker; no broad-token or branch-control bypass. No required product capability is silently reduced.
  • Local configured suite and exact-head PR checks pass; resource ownership/cleanup is verified. App selection and live fixture consent are not inferred from repository engineering authentication.

Non-goals and risks

No product policy database, background registration, full onboarding/pipeline UI, general SDK, App registration without PM designation, blanket repository permissions, production release, cross-platform evidence or adoption contract changes. The App may lack personal Project or creation coverage; preserve that as a critical feasibility result and obtain PM direction for a material alternative. A canceled request may already have affected GitHub; reconcile before claiming no effect. A planner fixture cannot prove token storage or worker isolation. Later product connections require OS-protected retained storage.

Sources and decision record

  • Device authorization: official verification, interval and error contract; browser exchange requires a secret.
  • Device token refresh: client secret exception for device-issued tokens.
  • Permission inventory and Project API: candidates for explicit live verification.
  • Registration URL prefill: a setup aid that does not submit or authorize registration.
