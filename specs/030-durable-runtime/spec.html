Outcome and requirements

One durable repository slot binds an Issue, Dev, captured policy/pipeline and worker epoch. Three active statuses reserve the slot: In Progress, In Review, Pending Review. Duplicate triggers share the reservation. Restart retains ownership and requires reconciliation; uncertain writes never become success or blind retries. R-02, R-05, R-17, R-33; NFR-10, NFR-17–NFR-20; F-06, T-02/T-11/T-15, S-15.

State and trust contract

The GitHub node identity is authoritative across clones. Local aliases bind real common-directory path plus device/inode; a reused path, conflicting origin or different remote identity fails closed. The first claim atomically captures the latest valid policy, configured available Dev, pipeline hash, limits and monotonically allocated epoch. A unique partial SQLite index enforces one unreleased run per repository, independent of UI or Project status. A duplicate command with changed binding fails; the same Issue returns the existing claim without another epoch.

Each database client has a private host session. An existing running claim viewed by a new client is recovery-required; that client cannot dispatch with the former epoch. Resume requires fresh repository readback, verified former-worker termination and resolved uncertainty, then atomically advances the epoch. Pause/Stop requests and verified results are separate; neither releases the Issue or erases work. Actual restricted worker transport, OS termination/resource verification and local UI are D-09.

The typed action ledger stores operation, original command, run/Issue/repository/step/epoch, exact candidate, request/precondition/expected-result hashes, attempts, deadline and observations. It never stores credentials, arbitrary request bodies or raw provider responses. Persist prepared intent before dispatch; persist dispatched state before returning permission to the host dispatcher. Only trusted complete readback can verify the expected result. Lost response or failed readback remains uncertain and blocks another mutation. Verified absence can prepare a bounded retry of the original action; denial/permanent failure cannot. Dispatch rechecks captured/current authority, epoch and deadline. SQL and GitHub do not share an atomic transaction.

Captured limits, action attempts and deadlines survive reopening. This slice enforces ledger retry/deadline limits; live provider metering, full pipeline routing and scheduled-run budgets are later slices. A verified inactive readback and verified stopped worker can release a claim. Done additionally needs the captured Development integration step's verified merge evidence. Worker exit alone never changes Issue state or releases the slot.

Non-goals and limitations

No remote test repositories, provider login loop, complete scheduler/executor, arbitrary authenticated proxy, full PM UI, installer or cross-platform qualification. No changes to framework adopters, configured lifecycle controls or user-owned documents. D-09 must connect the ledger to a real restricted worker; later GitHub orchestration must implement typed complete readback and conditional writes. Fixture observations prove core enforcement, not live endpoint/OS behavior. No universal exactly-once claim.

Risks and recovery

SQLite serializes local writers; external GitHub changes can occur after inspection and must be checked at the actual write. Private session fencing protects host dispatch but is not OS isolation. Missing inspectors fail closed. A persisted clock watermark rejects backward wall-clock movement instead of extending an action deadline; an expired deadline never resets on retry or recovery. Backups remain inside the private app-owned root and are never automatically substituted over a damaged database. Unknown versions/corruption preserve evidence for explicit recovery. Backup retention and encryption-key handling for credentials are later delivery/privacy slices; credentials remain outside this ledger.
