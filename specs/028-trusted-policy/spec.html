Canonical state and resolution

Versioned state contains schema version, host preferences/ceilings, global repository defaults and repository overrides keyed by verified opaque repository IDs. Host-provided verified catalogs list repositories, connections, Dev/model capabilities, extensions and host abilities. Models and renderer payloads cannot modify those catalogs or supply arbitrary credentialed destinations.

Field definitions cover all fifteen Settings categories. S-15 is a read-only inspection view, not an editable security mechanism. S-01 stores authorized opaque connection references only. Credentials are never policy values. Shipped defaults follow the accepted matrix: no selected autonomy preset, PM–agent drafting/explicit PM creation, recommended supervised template, no Dev/fallback/takeover, scheduling/background/login off, workspace/task grants only, finite budgets/retries/deadlines, local delivery, bounded retention, telemetry/upload/sharing off, system appearance and stable updates with no automatic installation.

Repository value overrides global, then shipped default. Lists replace. Reset deletes an override. Host-only fields reject repository/global placement. Previews show configured/effective value, source, scope, timing and consequences. Policy revision invalidation is installation-wide: a changed global/host version requires a fresh proposal even for an unrelated repository. This conservative check prevents stale inherited previews; narrower revision tracking is unnecessary at this scale.

Permissions intersect configured grants, global ceiling and actual qualified host abilities. Repository edits cannot expand the ceiling. Tightening recomputes allowed captured grants; expansion is usable only by a new run. Captured connection/Dev/extension references must still be present and enabled now. Budgets requiring unavailable provider metrics are rejected. Service activation and unsupported telemetry capabilities are unavailable until their qualified adapters exist; storing a boolean never registers a service.

Pipeline representation

A definition has an entry and 1–64 typed steps. Every step has a unique ID, readable label, kind, required permissions, inputs, expected result, produced evidence, success/failure/feedback routes, finite retry limit and finite visit limit. Routes resolve to another step or the complete/blocked terminal. Every step is reachable. Every Development route reaching complete must pass PR integration; at least one valid completion path exists. Cyclic feedback has a finite per-step visit ceiling. Fully Autonomous presets require no PM gate in either definition. Release runs follow Development integration; a release definition cannot manufacture a pre-integration execution claim.

No custom shell source, general HTTP destination or model-authored permission grant is embedded in a pipeline. Extension references resolve only to approved pinned catalog entries. Captured versions remain unchanged; restore copies validated earlier content into a new current version and a fresh PM proposal.

Trusted apply and durability

  1. The host registers its local PM control WebContents and exact custom-protocol document. Only that main frame, alive and at the exact document URL, may reach the control adapter. No caller-supplied role, origin, window ID or approval string supplies authority. Host-owned context binds conversation and target; a context switch invalidates outstanding commands.
  2. A direct PM input receives an opaque input ID and a deduplicated command identity. Capture source text as data, bounded and never interpreted as approval by this core. Editing/deleting the original input invalidates it. Execution data can suggest a validated description but cannot obtain the writable control handle.
  3. Prepare one typed proposal against a current revision, original input/context, target, canonical payload hash and bounded expiry. Compute before/after and affected repository values from stored state. Duplicate preparation returns the unchanged proposal; changing a reused request identity fails.
  4. A fresh direct PM apply operation binds to that exact proposal/hash and current context. Transactionally recheck input validity, expiry, revision, scope, catalog/ceiling constraints and consumed status; append one immutable version and consume the proposal. Repeated application reports its existing consumed outcome, creating no second version.
  5. Reopen verifies schema, stored content hash and complete typed state. Unknown schema/corrupt state fails closed without resetting policy. Proposal/input/apply records survive restart; historical versions remain readable. Restoration is a new proposal/version, never an in-place history edit.

Electron renderer content remains packaged local code under strict CSP. Agent text is rendered as text, never executable markup. The core authenticates the trusted surface, not a physical person cryptographically. Direct-input routing belongs to the trusted renderer/preload; quoted/transcript/model data has no dispatch path. Native qualification must exercise an allowed registered sender and a rejected independent sender. No generic loopback control endpoint.

Acceptance checks

  • One actual allowed apply, one immutable new version, correct durable preview/readback and consumed outcome after restart.
  • Inherited global changes, explicit overrides, list replacement and reset removal; all categories and accepted defaults inspectable.
  • Zero mutations for unknown fields, secrets/control-disabling/roadmap keys, host override, unsupported capability/budget, invalid graph, autonomous gate, altered hash, wrong/stale target/context/input, expired/duplicate proposal and worker-origin apply.
  • All complete Development routes include integration. Earlier captured definition survives edit/restore. Revocation reduces captured permissions without granting expansions.
  • Electron pinned runtime executes SQLite and the actual registered sender check; a separate renderer cannot obtain apply authority. Record current-Mac results only.
  • Run node --test desktop/core/*.test.mjs, npm run check, compatible native qualification and exact-head PR checks. No application build enters Actions.

Risks, recovery and non-goals

Policy state is protected from future isolated workers only if D-09 never mounts it or gives the worker control authority. Owner-only file modes, hashes and immutable records are defense in depth, not protection from a same-user host process, administrator or compromised broker. No OS isolation claim, credential storage, external effect ledger, background helper, new sign-in, production UI, installer or Windows/Linux support is delivered here. D-08 owns reservations/action recovery; D-09 owns real worker enforcement; D-10 owns secure retained connections.

Tests allocate a new exact private directory and own only those processes/windows/files. Always close databases, quit native test processes and remove/read back that directory. Preserve the build dependency for the continuing goal and all unrelated applications/user work. Storage failures never reset or overwrite existing state.

Observed implementation review

Focused checks now pass 12 scenarios. Test-driven review fixed permission regrant to an older captured run, cross-context input invalidation, and unnecessary plaintext input retention. Policy apply persists a revocation revision in the same transaction; an old run remains denied after regrant. New runs can use the expanded policy. Dev/extension version selection remains pinned; explicit extension disable is a separate immediate revocation. Original input provenance stores a hash, not raw PM text. Direct PM text remains data; this core does not interpret quoted approval as a command.

Actual native check passed on Electron 44.4.5 / Node 24.21.0 / SQLite 3.53.4 / Chromium 152.0.7977.130. The registered renderer applied one version, repeated apply produced no second version, a separate renderer at the same origin was denied, forged role data was denied, agent-like markup stayed text, and reopening preserved both current and historical policy.
