# Monitor Pipeliner Updates

Use when the user explicitly asks to schedule, watch for, or receive notifications about Pipeliner updates, or to change/remove an existing such monitor. Installing this skill, invoking it without a scheduling request, or requesting a framework update does not authorize creating an automation. A one-time check can remain read-only. This is direct maintenance: never create or require a GitHub Issue, reserve an active slot, move Project cards, or ask for Issue-creation/completion approval. Execute within the user's requested scope and identify the target repository and monitor in communication, as allowed by the explicit maintenance exception in `AGENTS.md`.

1. Resolve the requested target and verified framework upstream using [upstream identity and provenance](../pipeliner-update/references/upstream.md). Confirm the tracking channel and applied baseline or disclose that it is unknown. Read the target's published default-branch provenance, not a pending update branch. Missing target, cadence, timezone, or material notification preference requires a focused question and a wait; use existing explicit preferences when available.
2. Discover the current environment's supported persistent automation tools and read their live schemas. Verify the scheduler can access the target, upstream, and persistent notification state when it runs. In Codex, discover `automation_update` and follow its current host-specific instructions, including existing-job discovery and heartbeat versus standalone selection. In other environments use their native supported scheduler. Do not assume a tool name, payload, project ID, host availability, or capability transfers between providers.
3. If no supported scheduler exists, say that no automation was created and explain that a one-time check or a supported scheduling environment is needed. Do not install cron jobs, launch agents, GitHub workflows, daemons, or third-party services as a workaround without a separate explicit request. Do not modify credentials to make unattended access work.
4. Inspect existing monitors for the same target/upstream and read their schedules, prompts, and state. Update the matching monitor instead of duplicating it; resolve ambiguous matches before mutation. Preserve unrelated fields and notification preferences. For pause/removal, use the native API on the verified matching job and read back the result.
5. Prepare a detection-only prompt using [the monitor prompt contract](references/monitor-prompt.md), with resolved identities, schedule/timezone, baseline semantics, and durable deduplication behavior. The user's explicit scheduling request authorizes creation within that scope; do not ask for redundant confirmation once all required choices are known. Apply with the supported automation tool, then read back the saved ID, enabled state, schedule/timezone, target, and prompt. Distinguish a proposed or queued job from a confirmed active monitor.
6. Report what was scheduled, where it runs, when it runs, what triggers a notification, the saved identifier, and any access/state limitations. Provide PM Testing steps to inspect the saved job and perform a supported read-only test run if available. Do not claim successful unattended execution until a run has produced evidence. Keep unchanged successful checks quiet; notify only on a new upstream revision or meaningful failure/recovery requiring attention, respecting the user's notification preferences.

Detection never authorizes installation, Issue creation, Project transitions, PR creation, application deployment, or changes to the applied baseline. When an update is found, point the user to `pipeliner-update`; wait for update authorization.
