Project-agnostic delivery governance

Pipeliner

One evidence-first path from a coherent GitHub Issue to an exact, verified release and clear PM Testing. The repository profile supplies project-specific details; the lifecycle supplies the safety contract.

Lifecycle

1 · Backlog

Research, clarify, approve, create, classify, and read back one implementation-ready Issue.

2 · In Progress

Reserve the single active slot, specify, implement test-first, validate, and publish a linked pull request.

3 · In Review

After local QA turns and cleanup, verify the exact candidate and guide the next release or completion gate. Local PM Testing waits in In Progress.

4 · Done

Release through the configured strategy, verify, receive candidate-specific PM acceptance, then close and read back.

Issue-based communication

Every progress update, blocker, testing handoff, release result, approval request and acknowledgment, and completion message identifies the owning GitHub Issue first. Pull requests remain critical supporting evidence for review, checks, merge state, and candidate identity.

For Issue #42 implemented by PR #57, report “Issue #42 is awaiting PM Testing; PR #57 is merged.” The default completion approval is Approved. Use the Issue number, never the PR number. Preserve other configured gate phrases and bind every approval to the Issue, specific gate, and exact unchanged candidate.

Report the Issue complete only after all configured gates and live readback pass. If no Issue exists or linkage is unclear, state the limitation and follow Issue-creation governance without inventing an identifier.

Agent-owned Project movement

Tell the agent to start work, work a specific Issue, or review. It selects ready work by configured priority and then oldest Issue number when no target is specified, honors the sole active Issue, and invokes subsequent skills itself. Testing approval or feedback resumes the same Issue without another start command. Read-only audits remain read-only; completion does not start unrelated work.

The agent performs routine GitHub Project transitions and immediately verifies the resulting Status, metadata, assignment, Issue state, linkage, and active count. The PM never has to drag a card to keep the pipeline coherent.

Exactly one Issue may be active. Merge, green CI, deployment health, and silence are evidence—not completion or approval.

Every official approval response is exactly Approved. The request identifies the Human PM, Issue or draft, candidate, gate and authorized outcome. Final source-only/native-only QA approval authorizes integration, verification, closure and cleanup without another Issue-completion confirmation. All required pairs still test and approve the latest candidate. Distinct release-stage testing and Production authorization remain scoped decisions; never infer scope from the shared approval word.

Release strategies

Immutable promotion

Build once, verify the review candidate, obtain exact approval, and promote the same artifact without rebuilding.

Direct Production

Complete local QA, obtain Production authorization for the reviewed source, merge and deploy, then verify final identity before Production PM Testing and completion approval. Do not request a future deployment ID or invent staging.

Multi-environment

Validate the same code candidate independently on every required native host or environment. One approval cannot substitute for another.

Project Manager QA

Every Issue or aggregate release handoff gives a full Showcase: scope and owning Issue, change summary, Agent findings (explicitly none when empty), test results, exact target, prerequisites, numbered actions paired with expected results, regression checks, limitations, candidate identity, next outcome and the precise configured approval phrase.

When evidence cannot resolve a material choice, the agent asks focused questions only in a final ordinary message marked Question: and ends the turn immediately. All task work and tool calls stop until the Human replies at their own pace. Native question controls, structured question tools, background continuation, polling, sleep loops, timers, reminders and inferred answers are prohibited. Save answers before asking and reuse them on resume. Actual approval is bound to the exact candidate and gate.

Review resumes while In Progress or In Review. Feedback after merge returns the same Issue to In Progress and the agent creates a fresh supporting PR. Pre-release and final deployment identities are recorded at their respective stages; changed trees or artifacts invalidate earlier approvals.

Repository discovery

Branch protection and rulesets are optional and never enabled by default. The agent asks the PM whether protection is wanted and, if so, which branches and rules to enforce. Existing controls remain unchanged until an explicit decision. Agent quality gates and PM approval still apply without branch protection.

Begin with an explicit target or intent to create a repository. The agent resolves missing name, purpose, owner, visibility and destination, then verifies access and identity. Failed access is not proof of absence. Existing customized policies and unrelated work remain protected.

The conditional interview reuses saved answers and asks only unresolved applicable questions about runtime systems, Agent Dev/Human PM pairs, local QA, setup, cleanup, release destinations and optional cycles. Legacy profiles remain readable but require explicit participant/circulating migration before a new QA sequence; old approvals are never synthesized into new passes. Material unanswered choices pause dependent work. Bootstrap does not deploy the application.

Installed commands come from the target profile, with Node.js 22+ required only for framework tooling. The installer runs from a reviewed upstream checkout. Project audits use the target identity and mapped fields, support user and organization owners, and fetch complete pages. Missing visibility policy preserves the observed value; Pipeliner's public example is never an adopter default.

Local QA and ownership

QA turns are independent of release destinations. Devs are Agents with accountable GitHub logins; PMs are explicitly registered Humans. Each turn pairs an Agent, environment and Human PM; several pairs may share a PM. One Agent may test Windows and macOS; two Agents may both test Windows. Each required turn runs the full suite locally and records the exact candidate, owner, environment, session, results, PM Testing and cleanup.

The current pair finishes on the latest candidate before the next stale pair, scanning forward and wrapping through configured order. Every pair must pass on that candidate; latest rounds never fall back to an older pass after failure. Candidate changes invalidate all shared QA, including documentation/evidence-only changes. One pair needs no transfer bookkeeping. Otherwise, the outgoing owner verifies every gate and confirms the exact candidate is available to the next environment. The incoming owner verifies identity and acknowledges pickup. Waiting remains In Progress on the same Issue; missing hosts never count as a pass.

Application, native-package and container-image builds stay on compatible local systems. GitHub Actions retains reviewed lightweight checks, including inspection of every indirect command chain. Local evidence never fabricates a GitHub check result.

Track test-owned processes, containers, images, volumes, artifacts and workspaces by exact identity. Clean up after successful and failed runs, preserve unrelated resources, and verify removal. Resources retained for PM Testing need an owner and cleanup trigger; final removal remains a required gate.

Framework updates and optional monitoring

Adoption and framework updates require no PM Testing, PM acceptance, or bootstrap-completion approval. The agent runs test suites and agent testing, remediates findings, reruns affected checks, verifies publication and cleanup, and reports completion. Future application QA and release PM gates remain configured but do not block bootstrap.

Use pipeliner-update to incorporate a reviewed upstream revision into an existing repository. Preserve its configuration and custom policies, validate the reconciled installation, record the applied framework commit, and publish the verified maintenance update. Framework updates and update-monitor setup run directly without creating or requiring GitHub Issues, consuming the active slot, or asking for Issue approval. Existing repository protections still apply. Missing historical provenance remains unknown until verified.

Use pipeliner-monitor-updates only when the user requests scheduled detection. The agent discovers the environment's supported scheduler, resolves the schedule, avoids duplicate jobs, and verifies the saved automation. Unsupported environments receive an honest limitation. Monitoring reports meaningful changes and never installs updates; adoption does not create a monitor automatically.

Installed repository home

Installed skills use their own canonical installation, Git root, AGENTS.md and repository profile, verifying every fetch and push origin identity. The no-argument installed home resolver is anchored to its script location, not the caller's working directory. First adoption still needs an explicit target; auxiliary repositories are never inferred.

Optional release cycles

A cycle uses the same 12 skills and explicitly ordered development, stabilization and final production phases, each with its own branch, environments, readiness, approval and promotion identity. Phases never become Project Status values. A target/milestone groups development Issues and a Release Issue owns aggregate validation.

Development Issues complete after their own paired QA, full Showcase, exact phase-branch integration and acceptance. This does not accept or deploy the aggregate release. Freeze exact scope before aggregate phase approval; stabilization rejects new features and requires verified forward-ports into declared development phases. Development and production phases have no forward-port targets.

Every pair and Human PM validates the latest aggregate candidate. Keep the Release Issue open through phase advancement, blockers, cleanup and final acceptance. Only the Human PM can pause it to free the single active slot for a blocker. Production mutation requires separate pre-release authorization; final production-phase approval and completion cover the verified released candidate.

The final phase kind production may mean native Stable distribution under the multi-environment strategy, with native-role environments. Verify the candidate and configured distribution, then complete aggregate QA and all-Human acceptance. Do not invent a service Production URL or invoke the Production skill without an actual configured Production destination. All four release strategies retain their meanings.

Source promotion proves source/tree continuity. Same-artifact promotion reuses the exact approved digest without rebuilding. Distinct-artifact promotion requires declared channel inputs, separately verified bytes and every PM's approval of the resulting digest. Preserve original QA records and separately prove intended merge/deployment transitions.

Candidate integrity

An approval belongs only to the configured source commit, Git tree, artifact digest, rendered configuration, deployment revision, native host, or validation session that defines that candidate. A material identity change invalidates approval and returns the work to verification.
