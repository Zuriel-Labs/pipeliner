Focused design

Use the existing navy, mint and lavender system. Pipelines are a Settings category with a Development/Release selector, explicit repository/global scope, effective source and current version, a readable step list, selected-step semantic fields and an exact before/after proposal. Every supported action has a guided plain-language chat equivalent. Numbered steps and readable names identify targets; no node IDs, JSON/YAML or authored commands are required. Native controls support keyboard, visible focus, 44px targets and status announcements. Current and captured active definitions appear separately. Show unavailable execution/capabilities honestly; definition editing does not grant them.

Risks and recovery

  • Branch graphs and failure/feedback loops can have different completion histories. Traverse state by route outcome and integration/QA state with finite node/step/visit bounds; do not treat reaching a gate or merge step as success.
  • Global edits can conflict with preserved repository overrides. The canonical resolver rejects an invalid combined state; preview names every affected repository. Do not silently overwrite its custom graph or widen its permissions.
  • Policy/catalog changes can stale a draft/preview. Preserve the original draft, show its base and require refresh/review; never migrate an active run to the new definition. Reopen retains applied versions and draft values, while old apply handles stay unusable.
  • Migration/backup failure leaves readable prior state and blocks mutation. Keep private backup ownership and compatible schema verification. No destructive rollback, global prune or credential export.
  • Definition permissions/custom inputs do not prove executable capabilities. Display declaration versus current availability; actual provider/supervisor/extension/native dispatch remains gated by qualified host controls.
