Issue #54 — verified installer staging

This implements the next bounded part of D-24, S-14, R-43, NFR-10/NFR-12, F-08 and T-18. The full outcome still includes native trust, explicit idle installation, compatible migration/rollback and scoped uninstall. A staged checksum is not evidence that those functions work.

Research and decision

Electron's updater API downloads an available update during its availability check and applies a downloaded update on a subsequent launch. Those semantics do not satisfy the agreed separate availability/download/install controls without additional qualification. Keep the existing signed metadata/history path. Implement an explicit host-only byte stage before the native installer. Use Node's existing async stream consumption and file-handle writes for backpressure and partial-write handling; no new dependency. These technical choices remain provisional until executed on the current candidate. Apple's notarization requirements remain separate mandatory native controls.

Specification and ordered plan

  1. Write one synthetic transport/storage regression before the implementation. Use real protected update history and an ephemeral signed publisher; qualify success, refusal, byte tampering, oversize/truncation, redirects/compression, private DNS, abort, stale authority, expiry and altered output ownership. Run only through admitted external storage.
  2. Accept only a trusted host history handle, exact source/current host context, a private canonical destination, explicit byte/free-space budgets, cancellation and an authority callback. No renderer URL, release, file path or qualification flag. Snapshot the freshly authenticated newer release from history. Reject absent/expired metadata, unsupported host, insufficient capacity or stale authority before dispatch.
  3. Reuse public-address and canonical endpoint checks. Resolve and pin one public address; keep TLS validation and reject redirects, compressed bodies and unexpected content types/lengths. Never send provider credentials or cookies. Stream into a uniquely created 0600 file under the exact owned 0700 directory. Hash actual written bytes, handle partial writes and enforce the signed byte ceiling before each write. Request and storage timeouts remain bounded; the host supplies a 100–1,800,000 ms deadline. This ceiling is provisional, not a measured download performance result.
  4. Await response/request/socket settlement, fsync the file, read back its checksum and verify unchanged ownership. Retain the verified file timestamps; after the signed-history refresh and directory fsync, check them again before exposing the host-only receipt. Refuse a same-inode, same-size rewrite after checksum verification. On failure remove only the original, unchanged owned partial file; preserve a replaced/altered path and return a fixed repair error. Close file/directory handles on every path. Preserve unrelated files and protected history. The installer must independently verify the stage before consuming it; a receipt does not prevent subsequent account-owner changes.
  5. After admitted focused and full checks pass, integrate staging into the explicit installation flow. Native Developer ID/notarization, idle-effect fencing, durable maintenance intent, compatible backup, replacement/relaunch, recovery and uninstall require their own implementation and actual T-18 evidence. Do not enable download from availability polling or label a byte stage as an install.

Acceptance and non-goals

The stage returns only after an authenticated available release matches the exact stored bytes/checksum, source history remains unchanged, authority remains current, and owned transport/writer handles settle. Every refusal preserves history and unrelated files. Cancellation waits for settlement and checks cleanup. The stage does not execute, mount, install, restart or publish anything; it does not change policy, service registration, keys or source trust. It remains outside packaged runtime inputs until an actual installer consumer is integrated.

Risks and verification

A checksum does not establish native binary trust. Retained source watermarks cannot be reset to admit a download. The 8 GiB signed asset ceiling is already enforced by the manifest; the supplied host byte budget may be lower. Filesystem metadata guards follow the existing protected-store pattern; this is not OS confinement against a user with control of the account. Interrupted or modified files remain held for recovery when ownership/content cannot be verified. Public TLS, real download throughput, power-loss and installer/migration behavior remain unqualified.

Generated fixtures/logs/caches use the admitted unique external run. Record results against the exact source in Issue #54. A focused synthetic-transport pass does not establish native download, installation, application-build or full-suite qualification.

Native trust and signed build identity — next implementation increment

Keep the same D-24 mappings. The local review builder currently records source/tree outside the app. Add a small canonical build identity resource before signing, so an installer can compare the signed bundle's version, host, source commit and tree with authenticated release metadata. Do not treat a development signature as distribution authority.

Apple's TN3127 defines Developer ID issuer/leaf certificate extensions and the Team ID constraint. TN2206 requires strict recursive signature verification and explains why bundles must remain unchanged after signing. Apple's trusted execution guidance recommends syspolicy_check distribution; the current Mac's manual states that it combines Gatekeeper, XProtect and related checks. A system assessment is separate from actual quarantined first launch and Human consent.

  1. Implement canonical build identity validation and bounded, unchanged regular-file reads. Add real-filesystem regressions for altered, linked, malformed and foreign identities.
  2. Implement one host-only Mac bundle verifier. Accept a canonical app bundle, a pinned publisher Team ID and authenticated release metadata. Require the fixed Pipeliner bundle identifier, Apple Developer ID issuer and application certificate, matching Team ID, hardened runtime, secure signing timestamp, no debugging/library-validation bypass entitlements, an arm64 executable and a successful current-Mac distribution assessment. Compare the signed build identity with the expected version/source/tree/host. Repeat signature/identity checks after assessment. Use fixed native commands with bounded output/time, cancellation and awaited settlement; never execute candidate code.
  3. Write a synthetic native-command regression before implementation. Exercise exact command arguments, refusal of development/wrong-team/invalid signatures, missing timestamp/runtime, policy denial, non-arm64 content, stale identity, cancellation and replaced files. Label mocked native responses explicitly. Run the real verifier against a retained Apple Development review app to prove refusal if an owned current artifact is available; a Developer ID/notarized positive case remains pending its actual credential/artifact prerequisites.
  4. Embed the identity resource in the existing builder before signing, include its digest in the build record, and preserve existing local-review labeling. Run focused checks, then the configured full suite through its qualified process route. Actual signed build/native installer checks require a compatible admitted run.

This increment verifies bundle trust; it does not mount, install, replace, restart, migrate, roll back, uninstall or publish. These remain required in the full Issue. An unavailable native tool or failed assessment refuses the candidate. No permission, provider, OS control, signature or notarization fallback is introduced. The verifier is current-Mac technical implementation; older Mac and other-host evidence remains pending.

The first actual native requirement probe on 6 October rejected the initial requirement syntax: unexpected token: not. The mocked regression had not established parser compatibility. Use the documented ! negation operator and negated entitlement existence predicates; Apple's requirement language treats a false Boolean value as absent for this test. Keep one shared requirement generator and execute it against the native parser. A successful development-signature refusal is negative evidence only; notarized Developer ID acceptance remains pending. The builder reads back the embedded identity after signing and compares it with the exact source/tree before constructing the review image.

Host-wide idle admission — implementation plan

The current view's busy flag cannot prove host idleness: Issue and Development managers retain tasks for other repositories, and the execution inventory may retain a worker after its repository reservation changes. D-24/R-43, NFR-10/NFR-12, F-08 and T-18 require an exclusive host admission fence before consuming an installer. This increment connects that fence to the actual host channels and execution authority; it does not enable an unqualified installer.

  1. Add one host-owned admission gate. Track every mutating renderer control through its complete dispatch promise. Allow only validated status reads and the exact update cancellation operation during an exclusive operation. Use Node's existing AsyncLocalStorage to identify the exact initiating control; a competing request cannot exempt itself. Acquire the fence synchronously before any asynchronous native inspection. Development and scheduling share its execution predicate.
  2. Inspect every registered repository, global Issue tasks, connection cleanup, manager operations, background cleanup, scheduler and durable uncertain effects. Defer while any repository reservation exists, including paused work; this conservative ceiling remains until a compatible migration and captured-run recovery plan is implemented. Do not cancel work, mutate its status, grant permissions or register a service to make installation eligible.
  3. Read all owned execution rows, including orphaned rows. Require no pending controls, tools, monitor work or live/blocked worker records. Under the fence, independently inspect each retained worker through the existing native environment; refuse unavailable or non-stopped observations. Recheck admission and the complete unchanged inventory after awaiting inspection. The monitor must not introduce a new inspection during the fence; worker preparation, execution and resume must refuse the fence independently.
  4. Route the explicit update action through this preflight. Busy or unverified work produces a fixed deferral. A successful idle preflight still reports the missing native installation and compatible recovery plan; the button stays disabled until that consumer is qualified. Release the temporary fence after success, failure or cancellation and await the operation's settlement. No durable replacement has occurred, so this temporary fence is not a recovery journal.

Acceptance: a competing control is refused before dispatch; status reads and cancellation remain authenticated; a non-selected repository or orphan worker prevents entry; a late change or cancellation prevents the consumer; an initiating control's detached continuation cannot reuse an expired exemption; all failure paths release admission without changing policy or work. Add one runnable asynchronous regression covering these boundaries and actual control-channel validation, plus assertions in the existing cross-repository Issue and protected update flow checks. Verify package closure, host syntax and the focused update checks in an admitted external run; run npm run check through its qualified process route before publication.

Non-goals and remaining risks: this increment does not download, mount, replace, migrate, roll back, relaunch or uninstall. Durable intent, compatible encrypted state snapshots, native replacement and scoped uninstall remain required. A process-local fence is not OS confinement or protection against the account owner. A mocked native observation does not prove real worker termination. Existing shutdown recovery remains authoritative.

Durable maintenance intent — ordered implementation increment

D-24/R-43, NFR-10/NFR-12, F-08 and T-18 also require an interrupted replacement to remain visible after process restart. Add one bounded, host-only maintenance record using the existing protected-file and authenticated update-record codec. Keep update release watermarks in their existing database; do not migrate or reset them. A separate private SQLite store has one monotonic revision, clock and encrypted intent. SQLite's atomic commit contract and synchronous documentation support DELETE journaling with EXTRA synchronization, including directory synchronization at journal removal. These controls do not establish physical power-loss qualification.

  1. Write a real SQLite/encrypted-record regression before implementation. Cover exact build/asset identity, one active intent, stale/concurrent handles, allowed phase order, failed transactions, future schema, altered ciphertext, restart persistence and refusal to cancel after replacement begins. Synthetic OS wrapping is labeled; it does not prove Keychain behavior.
  2. Persist preparing, staged, verified, replacing and relaunching phases, plus repair-required. Validate both build identities and require a newer target version. Bind ciphertext to the persisted revision. Only the exact live host token can advance or cancel an unchanged intent. Cancellation is available only before replacement; after effects begin, retain the record for the qualified recovery coordinator. Never clear it because a process exited, the app relaunched, or the target path happens to exist.
  3. Connect the saved record to foreground controls, Development, scheduling and execution supervision. A pending, invalid or unavailable record blocks new mutating controls and execution; authenticated status and update Stop remain available. Show fixed recovery guidance without paths, credentials or raw errors. Preserve PM policy, reservations and service settings. Inspect the record before creating an execution supervisor.
  4. Run the affected admission, startup, inventory and update checks through admitted external storage. Run the complete configured suite after its native process route is qualified. Native image attachment needs a Pipeliner-owned fixture route: the installed helper currently admits mounted fixtures only for Study. Do not impersonate that project or mount outside this Issue's external run.

Acceptance: an interrupted intent survives closing/reopening and keeps execution disabled; invalid authentication or future schema fails closed; failed/stale transitions leave the last intent unchanged; pre-effect cancellation is idempotently bounded to its live token; an intent after replacing cannot be cancelled. Include the new encrypted store in the existing data inventory and package only its runtime module. Non-goals: native mount/replacement, successful relaunch acceptance, compatible backup/rollback reconciliation, uninstall, publisher qualification and automatic recovery. The installer consumer still must verify cleanup before pre-effect cancellation and authenticate native state and compatible backups before resolving any post-effect intent. This record is not OS confinement or proof of update success. Compatible data capture before replacement — 7 October 2026

Continue D-24, S-14/R-43, NFR-10/NFR-12 and T-18/F-08. Reuse the authenticated encrypted migration archive in desktop/privacy/backup.mjs. Capture the three stores whose current payload schemas have migrations: Workspaces version 5, Development version 2 and Artifacts version 2. This capture does not authorize replacement or restoration. Settings, permissions, connection epochs, execution ownership, update watermarks and unresolved maintenance are preserved in their current stores; they must never be rolled back from this capture.

SQLite's backup documentation requires a consistent snapshot for live databases. These three stores already use DELETE journaling. Hold read transactions on every source before capturing any archive; refuse WAL, pending journals, unsupported schemas, integrity failures, changed ownership, stale admission or cancellation. A read lock prevents a concurrent SQLite writer from committing during capture. This is not confinement against an account owner who can rewrite files outside SQLite. Do not copy an active WAL or change journal modes to make capture pass.

  1. Write a real SQLite regression using synthetic records and real authenticated vault payload encryption; only OS wrapping is synthetic. Exercise multiple-store capture, writer refusal, current schema binding, encrypted bytes, cancellation, wrong permissions/schema and changed input. Confirm original files and unrelated records remain unchanged.
  2. Add cancellation/admission checkpoints to the existing archive writer and verifier. Keep the existing archive format, bindings, limits and failure cleanup. Reuse it through one host-only capture function, with fixed source names/schema versions and the installed build identity. No renderer-supplied paths, stores or qualification flags.
  3. Acquire and verify all read locks, capture and independently verify each encrypted archive, recheck source ownership and admission, then release every lock/descriptor. Return immutable receipts bound to the exact build. Retain completed encrypted archives if a later store fails; never publish a complete capture receipt for a partial set. An altered partial archive remains held for recovery under the existing archive cleanup rules.
  4. Integrate the resulting receipt into durable installer intent before enabling replacement. Native mounting, replacement/relaunch, compatible restoration, power-loss recovery and scoped uninstall still require implementation and actual native evidence.

Acceptance: a complete receipt contains exactly these three authenticated archives and the exact source build identity. All three SQLite sources remain unchanged; locks settle on success and failure. No credentials, PM authority, worker replay, app files, service registration or external data change. Non-goals for this increment: automatic restore, schema transformation, filesystem rollback, native installer completion or distribution approval. The existing 512 MiB archive ceiling applies per store; synchronous encryption latency remains to be measured before runtime integration.

Verification: externally routed node --test desktop/updates/backup.test.mjs desktop/updates/maintenance.test.mjs desktop/privacy/records.test.mjs, followed by the configured npm run check when its storage monitor is qualified. Keep source logic, native behavior and Human acceptance evidence distinct.
