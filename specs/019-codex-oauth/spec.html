Issue #19 · Codex OAuth and brokered tool qualification

Pre-code specification · M-0/D-03 · 28 September 2026. Baseline: Final Draft 1.0. Scope: current macOS 26.5.2 (25F84), arm64; installed Codex CLI 0.158.0-alpha.2.1 and Node 22.23.2. D-02 selected a no-host-mount VM worker, but did not qualify Codex or live auth. This Issue must not silently turn a provider feasibility check into a production adapter.

Sources and product trace

The official App Server protocol defines JSONL stdio, account/login/read/logout, model discovery, thread and turn lifecycle, streaming, interruption, dynamic tools, and mandatory approval requests. The official auth guide says cli_auth_credentials_store=keyring fails rather than falling back to a file; auto may fall back to plaintext auth.json. The current protocol marks dynamic tools experimental. Final Draft 1.0 requires ChatGPT-managed OAuth only (R-21), provider/model capability truth and zero-gate preflight (R-23), guided protected sign-in (R-38), scoped credentials (NFR-03), and no hidden provider gate or false success (NFR-30). Test protocols F-01/F-02 and Settings S-01/S-02 govern evidence.

Implementation plan and ordered tasks

  1. Inventory task-owned processes, homes, keys and fixtures; check exact CLI/host versions and generate the installed App Server schema into a disposable protected directory. Extract only the methods and fields this Issue uses.
  2. Build the smallest Node standard-library JSONL probe: spawn one local stdio App Server with a fresh task-owned provider home and minimal environment; handshake; inspect account/model/permission state; run managed login cancellation and logout safely. Scrub URLs, codes, tokens and account identifiers from durable output.
  3. After a real protected ChatGPT sign-in, exercise one synthetic thread/turn stream, read/resume and interrupt. Observe failure/expiry paths only where safely reproducible. Never infer a completed login or refresh from protocol schema alone.
  4. Qualify one fixed brokered synthetic workspace operation plus denials. Attempt direct built-in tool, descendant and provider-home access through the selected worker boundary. Verify exact before/after fixture bytes and classify any required approval prompt.
  5. Write a dark-mode qualification report with actual protocol/version, capability matrix, pass/fail/not-run outcomes and release-blocking limits. Review complete diff and security/privacy/cleanup evidence, run all configured local checks, prepare full PM Showcase and ask only exact-candidate PM Testing approval before merge.

Acceptance criteria

  1. Isolated provider home starts with no account and no inherited authentication. Managed ChatGPT sign-in succeeds only through provider-owned UI or device flow; cancellation/logout and any observed expiration behavior are accurately reported.
  2. Token values never appear in repo files, report, process arguments, worker environment or public output. The selected store has no silent plaintext fallback. Worker/provider-home separation is observed, not assumed from file permissions.
  3. One real turn provides event stream and completed/read/resumed state; interruption is demonstrated. Unsupported or unavailable lifecycle operations are explicitly pending.
  4. Only a typed, authorized synthetic tool request causes the intended workspace effect. Wrong-target, stale, policy, credential and malformed requests are denied; protected bytes remain unchanged. Any unmediated built-in tool path remains a blocker.
  5. Every mandatory provider/OS gate on tested paths is identified. A zero-gate core path is claimed only if an actual no-prompt end-to-end run is observed; otherwise mark it incompatible and retain the release blocker.
  6. Exact source/tree, versions, host, runtime/schema hash, tests, limitations, cleanup and PR checks are recorded. npm run check and local-mac QA suite pass. No unrelated adopter, Project or original-checkout changes occur.

Non-goals and risks

No production policy store, full Chat-First UI, GitHub/Ollama integration, live repository mutation, public installer, Windows/Linux proof or optional provider fallback. Critical risks: Codex's own built-in host tools may bypass the broker; OS keyring entries may not be isolated merely by CODEX_HOME; the experimental dynamic-tool API may change; a provider or managed policy may force an interactive gate. Document each as a blocker if unresolved. Actual PM browser/device sign-in is an external provider control, never simulated or bypassed.

Verification commands

From this Issue branch on the current Mac: codex --version; codex app-server generate-json-schema --out <task-owned-dir>; node --test desktop/codex/*.test.mjs; node desktop/codex/qualify.mjs --output <protected-report>; npm run check; git diff --check. Inspect auth storage/worker denial with redacted metadata only. Run no app/model builds in GitHub Actions. Tear down exact task-owned processes, homes, fixtures and generated schema after capturing nonsecret evidence; preserve any declared PM-retained auth only with owner and cleanup trigger.

Decision rule: one observed login is only connection evidence. It does not prove worker isolation, provider tool authorization, Fully Autonomous compatibility or the full Desktop product.
