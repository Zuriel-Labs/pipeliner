# Circulating local QA and paired ownership

Read `qa` independently of release topology. Devs are Agents; PMs are Humans. Require explicit Agent developer IDs with `kind=agent`, accountable `github` logins and available environments, Human IDs with `kind=human` in `qa.pms`, and `qa.mode=circulating`. Each ordered turn binds a developer, environment, Human PM and exact approval phrase. Cover every participating Dev and PM and every required QA environment; explicitly list required Dev/environment combinations as turns. Available environments describe capabilities; they do not require a turn for every accessible Dev/environment combination. Several turns may share a PM; one Agent may use several systems and several Agents may share an OS. These still require independent complete turns. Follow [legacy discovery and migration](../../pipeliner-adopt/references/discovery.md) before starting a new sequence with a legacy profile.

## Current pair and rounds

1. Read the active Issue's latest candidate and `currentTurn` from live evidence. Verify source commit, Git tree and every `qa.candidateIdentity` component against its authority. Shared identity excludes host-specific sessions/artifacts, which remain separately bound to the corresponding turn and release identity. Never transfer one platform's artifact approval to another.
2. Keep the current Agent Dev/Human PM pair responsible through findings, remediation, full retesting, Agent review, Showcase, actual Human approval and verified cleanup on the latest candidate. A change invalidates all earlier shared QA, including documentation/evidence-only changes. Do not jump to the first pair when a middle or last pair finds a problem.
3. After the current pair completes, scan forward through configured turn order, wrapping as needed, and select the next stale/incomplete pair. Skip only pairs whose latest records pass on the latest candidate. Publish outgoing evidence and prove next-candidate availability before transfer. Assign the incoming Agent's accountable GitHub login, then read back assignment, Status, metadata, Issue state and the single active count. Incoming Agent verifies candidate identity and acknowledges pickup.
4. Keep historical rounds. Each turn's round is a unique positive integer; evaluate its latest round, never fall back to an older pass after a failure. Missing host, review, suite result, Showcase, actual PM response or cleanup remains pending. All pairs' latest records must pass on the same latest candidate before In Review. One pair needs no transfer bookkeeping, but retains every verification gate.

For three pairs A/B/C: if B changes the candidate, B finishes first, then C and A if stale. If C changes it, C finishes first, then A and B. Any later change invalidates earlier shared passes again. A pair finishing does not mean the full sequence or release is accepted.

## Complete local turn

1. Verify the configured compatible host, OS and architecture before pickup. Missing native hosts remain pending; containers/emulation do not prove required native behavior. Resolve prerequisites, dependencies, accounts, fixtures, ports, browser/native launch and readiness from the target profile.
2. Inventory task-owned resources before setup. Use a fresh task workspace where applicable. Run every environment setup and full suite command, including required builds, launch, behavior and security checks, plus repository-wide `quality.commands`. Record command, exit status and durable evidence without secrets. All application/native/image builds stay local, including transitive setup/quality commands; lightweight Actions checks do not replace local suites.
3. Complete Agent review and remediation on the prepared candidate before requesting Human approval. Present the full [Showcase](../../pipeliner-review-issue/references/pm-testing.md) for this exact pair. Record the actual Human response and candidate. Approval waiting keeps the same Issue In Progress; only the PM may authorize On Hold. Continue authorized cleanup/coordination after a response without requiring another skill invocation.
4. Track processes, images, containers, volumes, workspaces and temporary artifacts using exact identity, run ownership and creation evidence. Teardown on success and failure, including setup failure. `createTestWorkspace`/`removeTestWorkspace` provide only a marker-checked file boundary; private ownership tokens stay local and do not authorize removal of external resources. Verify PID identity/start time before stopping and exact resource absence afterward. Never globally prune, kill broadly, delete shared caches or remove user-owned untracked work.
5. PM-retained resources need an owner and cleanup trigger; eventual verified removal remains a gate. Durable release artifacts needed for delivery or the next host are not disposable temporary test outputs. Clean temporary copies and stale historical resources without destroying required candidate availability. Failed or unresolved cleanup blocks the turn.

## Evidence and evaluation

Evaluate with `node scripts/evaluate-qa.mjs <profile.json> <evidence.json>` using the exact [evidence format](../../pipeliner-maintain/references/evidence.md). Circulating evidence contains `candidate`, required `currentTurn`, historical `records`, required owning `issue` and `scope`. Each record identifies its turn and unique positive `round`, developer/environment, candidate, host/session, pickup and availability, full suite results, structured `review` and `showcase`, PM owner/phrase/candidate/evidence, and verified cleanup inventory. Every historical record's cleanup must pass too; append exact-resource `cleanupResolutions` for later removal rather than rewriting historical records. Record outgoing next-candidate availability for a transfer. Keep sensitive session details in protected evidence rather than public messages.

Legacy linear records are readable only as legacy evidence; do not reinterpret them as new circulating passes. Helpers validate supplied data, not Agent/Human authenticity. Read actual logs, PM messages, repository state and resource readback before recording completion. A helper reporting ready never authorizes a merge, deployment or Human approval.

After an authorized exact-tree merge, keep QA records bound to their original reviewed source candidate. Separately prove the resulting integration-branch tree and artifact continuity; do not rewrite old records to claim testing of the merge SHA or a future deployment ID. Only the verified intended transition preserves authorization. Unexpected tree, dependency, configuration or artifact changes require fresh rounds. Final release acceptance covers the resulting release identity. [Release cycles](../../pipeliner-maintain/references/release-cycle.md) rerun this complete paired loop on the aggregate phase candidate with every configured PM and turn.
